## 1. 요구사항 분석

제품은 PDF 편집기가 아니라 PDF 화면에 학습 상태를 덧붙이는 로컬 CBT다. 가장 큰 위험은 파일을 표시하는 일이 아니라, 공개 전 정답을 놓치지 않고 가리면서 문제·보기를 보존하고 올바른 정답을 해당 문제와 연결하는 일이다.

| 요구사항 | 현재 해석·반영 위치 |
| --- | --- |
| Electron·Vite·Vanilla JS·npm·PDF.js | 기술 선택은 사용자 요구로 확정. 버전과 패키징 방식은 Unit 0.2에서 결정 |
| 로컬 사용·외부 자동 전송 금지 | 앱 자산 로컬 번들, 권한/네트워크 제한, 오프라인 패키지 검증 |
| PDF 원본 불변 | 읽기 전용 입력, 별도 화면 레이어, 사용 전후 해시 검증 |
| 파일 선택·드롭·페이지·배율 | Phase 1에서 순서대로 구현 |

## 2. 빠진 내용과 요구사항 사이의 긴장

아래는 사용자 요구를 임의로 확정한 것이 아니라 **검토 가능한 기본 제안**이다. 문서 승인을 받기 전에는 구현하지 않는다.

| 쟁점 | 충돌·누락 내용 | 제안 및 결정 시점 |
| --- | --- | --- |
| 범용 PDF와 MVP 범위 | 자동 문제 분리는 Phase 4인데 임의 PDF로 CBT를 보장하려면 분리가 선행되어야 함 | 첫 MVP를 검증된 단순 프로파일로 제한. 동의하지 않으면 Phase 4 일부를 앞당겨 범위 재설계 |
| 해설 위치와 정답 추출 | 가릴 영역을 찾았다고 정답 번호를 안다는 뜻은 아님 | 두 결과를 독립 관리. 영역은 확실하고 답만 불명이면 공개는 허용하고 채점은 보류 |
| 정답 없음·복수 정답 | 미추출·충돌·복수 선택형의 처리 미정 | 4/5지 단일 정답만. 애매하면 `채점 불가`, 임의 채점 금지 |
| 보기 수 | 4지·5지가 예시로만 존재 | 사용자가 페이지별 4/5지 선택. 공개 후 잠금; 자동 보기 수 검출은 문제 분리 단계에서 재검토 |
| 페이지 이동과 문제 이동 | 한 페이지가 한 문제라는 전제가 성립하지 않음 | MVP UI는 페이지 이동. questionId는 독립적으로 설계 |
| 답 확인 전 화면 | 분석 시간이 걸리는 동안 원문이 먼저 나타날 수 있음 | CBT 모드 전체 페이지 덮개 → 분석·마스크 준비 완료 후 표시 |
| 자동 분석 실패 | 수동 보정이 MVP 밖이므로 대체 경로가 없음 | 실패 이유를 안내하고 기본은 가림 유지. 사용자가 `원문 보기` 또는 다른 페이지/파일 선택 |
| 가림과 Text Layer | 불투명 덮개 아래 텍스트가 선택·복사·접근성 트리에 남을 수 있음 | 가린 span 또는 공개 전 페이지 Text Layer 비활성화. 보안 기능은 아니며 접근성 한계 기록 |
| 상태 보존 | 앱 종료·페이지 재방문·재시도 정책 미정 | 페이지 재방문은 유지, PDF 닫기/교체·종료는 초기화. 영구 기록과 재시도는 Phase 5 |
| 실행 OS·배포 | OS/CPU·설치형/포터블·코드 서명 요구 미정 | Windows x64 우선 제안. 최소 OS와 로컬 패키지 도구는 0.2, 패키지 실행은 0.4 |
| 암호·손상·특수 PDF | 비밀번호·XFA·첨부·링크·스크립트 처리 미정 | 암호가 필요하면 MVP 미지원 안내. 동적 양식/실행 기능은 지원하지 않고 정적 페이지 중심 |
| 파일 크기·성능 | 최대 페이지·메모리·로딩 시간 요구 없음 | 1.6에서 기준 환경과 측정 결과를 기록한 뒤 제한 설정. 숫자를 현재 보장하지 않음 |
| Local First와 개발 설치 | npm 다운로드까지 인터넷을 전혀 쓰지 않는지 불명확 | 개발 준비는 다운로드 허용 가능, 배포된 기본 기능은 오프라인 필수로 구분 |
| 검증 입력 | 실제 PDF, 기대 마스크·정답 데이터가 없음 | 1.0에서 합성 샘플 준비. 실제 대표 PDF 확보 후 지원 범위를 확인; 지금 정확도 약속 없음 |

문서 검토의 주요 판단은 **① 제한된 첫 MVP 범위, ② Windows 우선, ③ 세션 메모리만 유지, ④ 암호 PDF 유보, ⑤ 불확실할 때 원문을 자동 공개하지 않음**이다. 이 기본안을 바꿀 수 있으며 선택지나 샘플이 없다는 이유로 이번 문서 작성은 중단하지 않았다.

## 3. 기술적 타당성과 검증 우선순위

아래 난이도는 설계 추정이다. 일정 견적이나 실측 성능이 아니다.

### 3.1 Text Layer 기반 해설/정답 위치 탐지는 가능한가?

**제한된 형식에서는 가능성이 높다. 범용 인식 정확도는 아직 검증되지 않았다.** 실제 분석 입력은 Text Layer DOM이 아니라 `getTextContent()` 결과다. PDF.js는 페이지의 텍스트 내용과 viewport를 제공한다. [PDFPageProxy 공식 API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-PDFPageProxy.html).

우리 설계 판단: 해당 출력에는 문제·보기·해설이라는 의미가 보장되지 않는다. 글자가 여러 항목으로 나뉘고 시각적 읽기 순서와 항목 순서가 다르거나, 수식·그림·윤곽선 글자가 의미 있는 텍스트로 나오지 않을 수 있으므로 줄/블록 복원과 문맥 검사가 필요하다. `정답 ③`을 읽는 난이도보다 “그 ③이 어느 문제의 답인가”와 “해설은 어디서 끝나는가”의 난이도가 높다.

우선 검증: 한글 분절과 짧은 `답`의 오탐, 정답·해설 순서, bbox 정확도, 해설에 포함된 그림·수식. **난이도: 텍스트 추출 중간, 영역 의미 추정 높음.** Unit 2.1~2.6에서 확인한다.

### 3.2 다양한 레이아웃을 어느 수준까지 규칙으로 처리할 수 있는가?

단일 열·명확한 제목·일관된 순서·동일 페이지 안의 완결 구조가 출발점이다. 키워드 사전, 줄 간격, 제목 경계, 열/블록 관계를 함께 쓰면 일부 출판 형식을 지원할 수 있다는 설계 가설이다. “모든 출판사에 공통인 정규식 하나”로 해결할 계획은 채택하지 않는다.

| 사례 | 첫 MVP 제안 | 장기 구조와 검증 |
| --- | --- | --- |
| A: 문제 → 보기 → 해설 → 정답 | 지원 프로파일 검증 대상 | 해설·정답의 별도 영역을 같은 questionId에 연결 |
| B: 문제 → 보기 → 정답 → 해설 | 지원 프로파일 검증 대상 | A와 순서를 바꿔도 영역 추정·공개·채점 일치 |
| C: 한 페이지 여러 문제 | CBT 미지원 안내 | Phase 4.2 여러 Question와 독립 Region |
| D: 문제의 다음 페이지 연속 | CBT 미지원 안내 | Phase 4.3 여러 pageRefs, 문제 연결 후보와 보정 |
| E: 해설이 다음 페이지에 존재 | CBT 미지원 안내 | Phase 4.3 문항-해설 명시적 연결; 다음 페이지를 무조건 연결하지 않음 |
| F: 텍스트 없는 스캔 | 원문 열람만, 분석 불충분 안내 | Phase 9 선택적 로컬 OCR과 좌표 역변환 |
| G: 출판사마다 다른 명칭 | 기본 키워드로 시작, 일치하지 않으면 보류 | 버전 있는 프로파일·수동 보정·Phase 5 규칙 저장 |

다단·반복 지문·분리된 정답표·복수 정답·키워드가 없는 해설까지 범위를 넓히면 잘못된 연결 위험이 급증한다. 프로파일은 고정 절대 Y값이 아니라 허용된 패턴과 관계, 실패 조건으로 정의한다. 새 파일이 기존 샘플과 비슷하다는 이유만으로 안전하다고 단정하지 않는다.

**잔여 위험:** 미지원 형식을 자동으로 완벽히 찾아내는 것도 어렵다. 모든 경고 없이 통과한 새 PDF의 누출 가능성을 0으로 보장하지 않는다. 지원 목록과 검증 한계를 사용자에게 알리고, 의심되는 조건에서 보수적으로 보류한다. 수동 보정이 실사용에 필수라는 결과가 나오면 MVP 범위를 재협의한다. **난이도: 높음.**

### 3.3 Canvas + Text Layer + Mask Layer가 적절한가?

**적절한 책임 분리다.** 원본 표시를 그대로 두면서 학습 상태에 따라 마스크만 변경할 수 있다. Text Layer는 추출 자체에 필수는 아니지만 향후 선택·접근성·검색에 활용할 여지가 있다.

추가로 필요한 것은 공통 viewport, 로딩/불확실 상태의 전체 덮개, 공개 대상의 questionId 소유권, 텍스트의 우회 노출 억제다. 화면 좌표를 단순 배율 곱셈만으로 처리하지 않는다. Canvas 내부 픽셀과 CSS 크기를 분리하고 렌더 취소·완료 순서를 맞춰야 한다. PDF.js 예제도 비동기 렌더와 Canvas 동시 사용 제한을 설명한다. [공식 렌더링 예제](https://mozilla.github.io/pdf.js/examples/).

**난이도: 중간~높음.** 좌표 Unit 2.2, 마스크 Unit 3.1, 프레임·상태 통합 Unit 3.7이 검증 관문이다. Blur보다는 불투명 Overlay를 먼저 택한다.

### 3.4 한 페이지 여러 문제에는 어떤 구조가 필요한가?

**페이지와 문제를 분리해야 한다.** PDF 페이지는 렌더링 단위이고 Question은 학습 단위다. Question 하나가 여러 페이지와 여러 해설/정답 영역을 가질 수 있고, 페이지 하나에 여러 Question이 놓일 수 있다.

제안 관계: `Document → Pages`, `Document → Questions`, `Question → pageRefs[] + regionIds[]`, `Region → page + rects[]`, `Attempt → questionId`. 첫 MVP에서는 pageRefs 길이 1과 임시 page-single 모드만 사용한다. 문제 번호 문자열도 문서 안에서 중복될 수 있으므로 영구 ID로 쓰지 않는다.

여러 질문이 공유하는 지문, 공통 해설, 애매한 경계는 단순한 다음 문제 번호 탐지만으로 풀리지 않는다. Phase 4.0에서 공유 영역과 공개 정책을 재검토한다. 현재 복잡한 그래프 DB나 전체 도메인 프레임워크를 만들 필요는 없다. **난이도: 구조 중간, 자동 분리 높음.**

### 3.5 스캔 PDF와 일반 PDF는 어떻게 구분할 것인가?

**페이지별 분석 가능성을 판정한다. 스캔 여부의 완벽한 이진 판정은 목표가 아니다.** 텍스트가 비었다고 스캔으로 확정하지 않고, 텍스트가 있다고 쓸 만한 페이지로 확정하지 않는다. OCR이 이미 포함된 스캔, 페이지 번호만 있는 이미지 페이지, 손상된 문자 매핑, 텍스트와 이미지가 섞인 문서를 고려한다.

1차 신호는 유효 문자열·문자량·문자 품질·좌표 범위다. 필요하면 이미지 연산과 면적을 보조 신호로 평가할 수 있으나 “이미지가 있으므로 스캔” 같은 규칙은 쓰지 않는다. `getOperatorList()`는 분석 자료를 제공할 뿐 의미 분류의 답을 제공하지 않는다. [PDFPageProxy 연산 목록 API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-PDFPageProxy.html).

결과는 usable/insufficient/unknown으로 표현하고 후자의 경우 자동 분석을 보류한다. 임계값·이미지 조사 채택 여부는 샘플을 본 뒤 결정한다. **난이도: 보수적 분류 중간, 높은 신뢰도의 분류 높음.**

| 1 | worker·모듈·로컬 자산이 패키지에서 안 열림 | 0.4 / 1.3 / 1.6: 개발 서버 없이 실행 | 조합·자산 경로 수정. 웹 보안 해제로 우회하지 않음 |
| 2 | 한글 추출/좌표가 화면과 다름 | 2.1 / 2.2 / 2.5: 원문과 bbox 대조 | 좌표 어댑터 수정 또는 미지원 표시 |
| 3 | 해설 끝 경계를 놓치거나 문제를 가림 | 2.4 / 2.6: 사람 기준 영역과 비교 | 규칙 수정·지원 범위 축소·수동 보정 일정 검토 |
| 4 | 문제/정답 연결이 틀림 | 2.6 / 3.5: 단일 답 근거 대조 | 보류. 잘못된 자동 채점 금지 |
| 5 | 첫 프레임/배율 변경에서 답이 노출됨 | 3.1 / 3.7: 느린 분석·빠른 이동 포함 실제 화면 | 전체 덮개와 준비 상태 원자적 전환 수정 |
| 6 | 장문·이미지 PDF에서 앱이 멈춤 | 1.6 / 3.7: 메모리·취소·연속 열기 | 자원 제한·캐시·해제 정책 보강 |

성공 사례만으로 검증하지 않는다. ROADMAP의 실패/미지원 샘플도 같은 비중으로 확인한다. 첫 MVP의 유용성은 지원 샘플에서 실제 풀이가 끝나는지로, 안전성은 누출·침범·오채점과 미지원 오승인으로 각각 평가한다.

## 4. 기술 결정 기록

상태의 의미: `사용자 지정`은 요구사항에서 선택된 방향이다. `제안·승인 대기`는 이번 검토의 추천안이다. `결정 유보`는 해당 Unit에서 증거를 수집한 뒤 확정한다. 승인 이후 변경 시 기존 기록을 지우지 않고 대체 결정과 이유를 덧붙인다.

### ADR-001 — Electron과 Vanilla JS

- 상태: **사용자 지정**.
- 결정: Electron + Vite + Vanilla JavaScript + HTML/CSS + npm을 사용한다.
- 이유: 로컬 파일을 다루는 데스크톱 앱과 사용자가 정한 단순한 프론트엔드 구성을 따른다.
- 대안/대가: React/Vue는 현재 도입하지 않는다. UI 상태·모듈 경계를 직접 관리해야 하며 Electron의 배포 크기·메모리·업데이트 책임이 생긴다.
- 재검토: UI 복잡성 때문에 현재 구조로 유지보수가 어려워질 때만 근거를 갖고 제안한다.

### ADR-002 — PDF.js를 표시·추출 어댑터로 사용

- 상태: **사용자 지정**; 어댑터 경계는 **제안·승인 대기**.
- 결정: PDF.js의 표시·텍스트·좌표를 쓰고, 문제 의미 분석은 별도 모듈에 둔다. 전체 generic viewer를 무조건 복제하지 않는다.
- 이유: 필요한 데이터에 접근하면서 CBT UI와 수명 관리를 직접 제어하기 위함이다.
- 대가: 글꼴·자산·메모리·취소·좌표 정렬을 직접 검증해야 한다. PDF.js API 문서의 draft/master 내용이 선택한 안정판과 같다고 가정하지 않는다.
- 재검토: 버전 업그레이드 시 본체·worker·자산을 함께 검증한다.

### ADR-003 — 첫 MVP의 단순 형식 지원

- 상태: **제안·승인 대기**.
- 결정: 같은 페이지의 단일 문제·단일 열·4/5지 단일 정답과 검증된 A/B 형식에 한정한다.
- 이유: 자동 분리·페이지 연결을 MVP 이후로 남긴 사용자 계획을 지키면서 검증 가능한 첫 결과를 만들기 위함이다.
- 대안/대가: 임의 PDF를 바로 풀 수는 없다. 범용 지원을 요구하면 수동 보정·문제 연결을 먼저 넣도록 일정 변경이 필요하다.
- 재검토: Unit 2.6 샘플 결과와 사용자 문서 구성에 따라 조정한다.

### ADR-004 — OCR을 MVP에서 제외

- 상태: MVP OCR 유보는 **사용자 허용 범위에서 채택한 제안·승인 대기**.
- 결정: 원래의 텍스트 데이터를 우선 분석한다. OCR은 Phase 9에서 로컬 실행부터 검토한다.
- 이유: 텍스트·좌표 정확도 문제와 OCR 오인식 문제를 한꺼번에 떠안지 않기 위함이다.
- 대가: 스캔/텍스트 불량 페이지는 CBT 불가. 원문 열람과 이유 안내는 유지한다.
- 재검토: 핵심 사용자 PDF가 대부분 스캔이라면 MVP 제품 범위부터 재검토한다.

### ADR-005 — 별도 불투명 Overlay와 안전한 보류

- 상태: 원본 불변·별도 레이어는 **사용자 지정**; 불투명 기본값과 전체 덮개는 **제안·승인 대기**.
- 결정: 개별 Region 마스크를 questionId에 연결한다. 준비 전/분석 불확실 시 전체 페이지를 가린다. 원문 노출은 별도의 사용자 선택이다.
- 이유: 한 가지 마스크 상태로 로딩 실패와 정답 공개를 혼동하지 않고 원본을 보존하기 위함이다.
- 대가: 미지원 페이지에서는 문제까지 덮이므로 편의성이 떨어진다. 자동 인식의 실수 자체를 없애는 보안 장치가 아니다.
- 재검토: 수동 보정·다문제·접근성 확장 시 공개 경계를 다시 검토한다.

### ADR-006 — 좌표는 PDF 공간, 레이어는 viewport 공유

- 상태: **제안·승인 대기**.
- 결정: 화면 배율과 무관한 PDF user space의 영역을 저장하고 표시할 때 투영한다.
- 이유: 확대·DPI·회전·창 크기에 따라 저장 좌표가 변하지 않게 하기 위함이다.
- 대가: bbox는 근사치이며 변환·글꼴·잘림 경계를 검증해야 한다. 단순 CSS 비율만 적용하는 방식은 채택하지 않는다.
- 재검토: Unit 2.2에서 API와 좌표 시험을 확정하고 Phase 4 수동 지정·Phase 9 OCR 좌표를 연결할 때 재검토한다.

### ADR-007 — 메모리 데이터와 조건부 채점

- 상태: **제안·승인 대기**.
- 결정: 현재 열린 PDF의 상태만 메모리에 유지한다. 영구 DB는 만들지 않는다. known 단일 정답만 채점한다.
- 이유: 학습 기록을 Phase 5로 분리하고 분석 실패가 오답 데이터로 누적되는 것을 막기 위함이다.
- 대가: 종료 후 복원되지 않으며 재시도 이력도 없다. UI에서 저장 범위를 설명해야 한다.
- 재검토: Phase 5.0에서 문서 해시·영구 식별자·변경 감지·마이그레이션과 함께 설계한다.

### ADR-008 — 격리된 Electron 경계와 오프라인 패키지

- 상태: Local First는 **사용자 지정**; 보안 경계·패키지 검증 방식은 **제안·승인 대기**.
- 결정: 파일 접근은 main, 좁은 연결은 preload, PDF 표시·학습 UI는 격리된 renderer에 둔다. 외부 의존 없는 로컬 테스트 패키지를 만든다.
- 이유: 로컬 PDF도 안전한 입력이라고 전제할 수 없고, 개발 서버 성공만으로 실제 설치 앱 동작을 검증할 수 없기 때문이다.
- 대가: 파일 드롭·IPC·CSP·자산 프로토콜에 대한 통합 시험이 필요하다. 드롭은 폐기된 File.path 가정 대신 선택 버전의 지원 API를 사용한다. [Electron webUtils](https://www.electronjs.org/docs/latest/api/web-utils).
- 재검토: 0.2~0.4에서 main/preload 모듈 형식·허용 API·프로토콜·패키징 도구 확정. 서명과 공개 배포는 후속 검토다.

### ADR-009 — 검증을 독립 Unit으로 관리

- 상태: **제안·승인 대기**.
- 결정: 1.6, 2.6, 3.7 검증 관문과 2.5 선행 실행을 추가한다.
- 이유: 렌더링, 좌표, 인식, 공개 타이밍은 각기 다른 실패 원인이기 때문이다.
- 대가: 눈에 보이는 기능 증가가 없는 작업이 포함되지만 추후 오류 원인 추적이 쉬워진다.
- 재검토: Unit이 지나치게 커지면 번호를 보존하며 하위 작업을 분리한다. 테스트하지 않은 항목을 완료로 바꾸지 않는다.

### ADR-010 — AI는 기본 CBT와 분리

- 상태: **사용자 지정**.
- 결정: AI 요약·암기 포인트·유사 문제는 Phase 10의 선택 기능이다. 지금 서비스 코드·API 키·SDK를 만들지 않는다.
- 이유: 인터넷·제공자·비용·개인정보 정책이 기본 학습 기능의 사용 조건이 되면 안 된다.
- 대가: 생성 품질, 전송 동의, 로컬 모델 가능성은 나중에 별도로 검증해야 한다.
- 재검토: 10.0에서 서비스 경계와 데이터 전송 범위를 먼저 승인받는다.

### ADR-011 — Unit 0.2 런타임·지원 대상·의존성 고정

- 상태: **채택 — 사용자의 Unit 0.2 착수 요청에 따른 구현 결정**, 2026-08-31.
- 결정: 프로젝트 지원/검증 대상은 Windows 11 x64. 개발 Node 24.19.0, npm 10.8.2를 검증 기준으로 삼고 Node 24.19 이상인 24 LTS만 허용한다. `.node-version`과 `.npmrc`/engines 및 실행 전 검사로 버전 실수를 안내한다.
- 고정 직접 의존성: Electron 44.0.0, Vite 8.2.2, `@electron/packager` 20.3.0, Prettier 3.9.6. npm 레지스트리 metadata와 설치된 package.json을 확인했으며 package-lock.json으로 전이 의존성을 고정했다.
- 이유: Unit 0.2 당시 시스템 Node 20.19.1은 지원 종료 상태여서 사용하지 않았다. 시스템 Node나 영구 PATH를 바꾸지 않고 별도 Node 24.19.0으로 개발·검증했다. 이후 확인한 환경은 ADR-015와 [README](../README.md)를 따른다. [Node.js 지원 상태](https://nodejs.org/en/about/previous-releases).
- 플랫폼 구분: Electron 자체는 Windows 10 이상을 안내하지만 프로젝트가 Windows 10까지 검증했다는 뜻은 아니다. 이번 최소 지원 대상은 실제 검증 환경인 Windows 11 x64다. [Electron 공식 플랫폼 안내](https://github.com/electron/electron#platform-support).
- 확인 결과: Windows build 26200 x64에서 기본 실행 통과. Electron 내부 런타임은 Node 24.18.1 / Chromium 152.0.7977.54로 개발용 Node와 별개다.
- 추가 발견: Electron 44는 npm 패키지 설치 후 바이너리를 지연 다운로드한다. `npm run setup:electron`으로 공식 설치 명령을 명시적으로 실행하도록 했다. 최초 바이너리 준비에는 인터넷이 필요하며 앱의 원격 서비스 의존성을 뜻하지 않는다.
- 재검토: 업데이트 시 lockfile과 실제 런타임 조합을 함께 확인한다. Windows 10/ARM64/macOS/Linux 지원을 자동으로 확대하지 않는다.

### ADR-012 — ESM main/renderer, CommonJS preload, 두 실행 경로

- 상태: **채택 — Unit 0.2 구현 및 기본 연결 확인**. ADR-001/002/008의 현재 필요한 경계를 구체화한다.
- 결정: main과 renderer는 ESM, sandbox preload는 `.cjs`를 사용한다. preload는 읽기 전용 `runtimeInfo`만 노출하며 IPC·파일 API는 아직 만들지 않는다. [Electron sandbox preload 제약](https://www.electronjs.org/docs/latest/tutorial/esm#sandboxed-preload-scripts-cant-use-esm-imports).
- 개발 경로: Node 실행 스크립트가 Vite 준비 완료 후 Electron을 실행한다. `127.0.0.1:5173`과 개발용 WebSocket만 허용하고 strictPort를 사용한다. main/preload 변경은 명시적 재시작이 필요하다.
- 빌드 경로: `local-cbt://app/index.html`로 dist의 HTML/JS/CSS만 제공한다. 사용자 파일 경로를 받지 않고 호스트·메서드·상대 경로·Windows 경로 문자를 검사한다. 자산 유형은 현재 필요한 것만 허용하며 PDF 관련 유형은 후속 Unit에서 추가한다. [Electron protocol API](https://www.electronjs.org/docs/latest/api/protocol#protocolhandlescheme-handler).
- 보안: Node 통합 비활성화, context isolation·sandbox·webSecurity 활성화, 권한·탐색·새 창 기본 거부. 개발 CSP의 inline style/루프백 WebSocket 예외는 빌드 CSP에 포함하지 않는다.
- 대가: 가벼운 확인 화면에도 수명/권한 경계가 필요하지만 이후 PDF 기능 때문에 격리 설정을 뒤집지 않아도 된다. 이를 Application Shell이나 파일 접근 구현으로 확대하지 않았다.
- 검증: Unit 0.2의 개발/빌드 자산 연결과 정상 경로 Console Error·pageerror 0을 확인했다. Unit 0.4의 패키지·경로 거부·CSP·권한 검증 결과는 ADR-015/016에 추가한다.
- 수정 근거: 실제 개발 명령 시험에서 GUI 프로세스의 `windowsHide: true`가 창을 숨기는 문제를 발견했다. Electron GUI만 `false`로 수정했고, 숨겨진 콘솔 helper와 사용자 앱 창의 역할을 구별했다. 수정 후 보이는 창 열기·닫기·서버 종료를 확인했다.

### ADR-013 — 공식 Packager와 최소 빌드 설정

- 상태: **채택 — Unit 0.2 설정 구현, Unit 0.4 실제 패키지 검증 완료**. 추가 결정은 ADR-015/016.
- 결정: Vite는 renderer만 빌드하고 Electron main/preload는 직접 실행한다. 공식 `@electron/packager`로 Windows x64 폴더/ASAR 패키지를 만들도록 명령을 준비했다. [Electron Packager](https://electron.github.io/packager/main/).
- 이유: 현재 main/preload 번들·자동 재시작·배포/서명 프레임워크까지 추가할 필요가 없다. Vite 전용 Electron 플러그인이나 Forge 전체 구성을 먼저 도입하지 않는다.
- 구현 세부: 설치된 20.3.0의 named export `packager`를 사용한다. electron/·dist/·package.json만 복사하며 개발 문서·스크립트·개인 파일·node_modules는 제외한다. 현재 런타임 npm 의존성이 없으므로 prune은 사용하지 않는다. 런타임 의존성을 추가하면 포함 규칙을 먼저 재검토한다.
- 출력: `release/local-pdf-cbt-win32-x64/`. 기존 출력은 자동 덮어쓰지 않는다. 설치 프로그램, 서명, 업데이트, 공개 배포는 수행하지 않는다.
- 한계: Unit 0.2 당시에는 Vite 빌드와 dist 실행만 확인했다. Unit 0.4에서 ASAR·독립 복사본·앱 네트워크 차단 조건을 검증했으며, 새 Windows/VM 전체 검증은 수행하지 않았다.
- 코드 형식: Prettier의 2칸·세미콜론·작은따옴표·LF를 적용한다. 기존 docs는 형식만 바꾸는 대규모 변경을 피하려고 자동 포맷 대상에서 제외한다.

### ADR-014 — Unit 0.3 기본 Shell과 읽기 전용 상태 표시

- 상태: **채택 — 사용자의 Unit 0.3 요청에 따른 구현·실제 화면 검증**, 2026-08-31. ADR-012의 연결 확인 화면만 확장하며 보안·파일 접근 경계는 유지한다.
- 구성: 한국어 정적 HTML의 앱 머리말, 빈 문서 작업 공간, 앱 상태 영역, 하단 안내. `src/main.js`는 초기화, `src/ui/runtime-status.js`는 전달받은 실행 정보의 표시만 담당한다. 기본 스타일과 Shell 배치는 CSS 파일로 나눈다.
- 상태: preload의 기존 읽기 전용 `runtimeInfo`로 연결 완료·Electron 버전을 표시한다. 정보가 없거나 버전 문자열이 비어 있으면 `Electron 실행 필요`와 실행 명령을 안내한다. `textContent`를 사용하며 색상과 문구를 함께 표시한다. `role="status"`·`aria-atomic`을 사용하고 장식 아이콘은 접근성 트리에서 제외한다.
- 배치: 기본 1120×760, 최소 640×480의 테두리 포함 논리 픽셀. 기본 화면의 빈 작업 공간과 상태를 함께 읽을 수 있도록 정했다. 콘텐츠 너비 56rem(기본 896 CSS px) 이하에서는 상태를 작업 공간 아래로 배치하고, 30rem 이하에서는 상태 항목도 한 열로 배치한다. 창이 작거나 확대된 상태에서는 잘라 숨기지 않고 문서 세로 스크롤을 허용한다. 창 크기·위치 저장은 추가하지 않는다.
- Local First: 시스템 글꼴·정적 인라인 SVG만 사용해 외부 글꼴/이미지·아이콘 패키지를 추가하지 않는다. 새 IPC, CSP 예외, 프로토콜 자산 유형도 필요하지 않다.
- 범위: 파일 선택/드롭·PDF 렌더링·페이지·배율 제어·학습 버튼을 만들지 않는다. 빈 화면이 드롭 영역이나 실행 가능한 CBT로 오해되지 않도록 미지원 상태를 명시한다. 새 상태 저장소·이벤트 버스·미래 서비스·의존성을 선행 구축하지 않는다.
- 검증: 개발/빌드 자산 모드의 실제 Electron 창에서 한국어 화면, 연결 정보, 4가지 창 크기와 최소 창의 200% 확대, 최소 크기 제한, 가로 넘침 없음·하단 스크롤 도달, 기존 격리 설정을 확인했다. 정보 없는 상태는 개발 모드의 표시 함수에 `undefined`를 전달해 확인했다. 확대는 검증 도구에서 적용했으며 앱 확대 기능 구현이 아니다.
- 제한/인계: Unit 0.3 정상 화면 경로의 renderer Console Error·pageerror·경고는 0이었다. 창 생성 직후 즉시 종료한 첫 시험에는 내부 GPU 진단 로그가 있었고, 당시 화면 표시 후 정상 종료에서는 재현되지 않았다. Unit 0.4의 후속 결과는 ADR-016/OPEN-09을 따른다. 스크린 리더·다중 모니터·Windows 디스플레이 배율별 실사용 검증은 수행하지 않았다.
- 재검토: 파일 열기는 Unit 1.1, 드롭은 1.2, 렌더링은 1.3, 학습 UI는 Phase 3에서 필요한 제어와 상태를 추가한다. 실제 PDF 레이어가 생기면 세로 스크롤의 소유 영역을 다시 정한다.

### ADR-015 — 반복 가능한 환경 검사와 로컬 패키지 검증 범위

- 상태: **채택 — Unit 0.4 주요 검사 통과, 종료 진단은 OPEN-09로 추적**, 2026-08-31 작성 / 2026-09-01 갱신.
- 도구: Node 내장 테스트 실행기로 자산 프로토콜·요청 허용 목록·CSP 16개를 검사한다. 실제 Electron의 개발/빌드/패키지 3경로는 개발 전용 playwright-core 1.62.1로 제어한다. 실제 Windows 닫기 동작은 PowerShell 종료 검사로 별도 반복한다. 별도 브라우저·제품 런타임 의존성은 추가하지 않는다. 도구 버전은 npm metadata와 설치 파일을 확인해 고정했다.
- 실행 기준: 이 Unit의 실제 환경은 Windows 11 x64 build 26200, 개발 Node 24.19.0(별도 런타임) 및 24.20.0(현재 시스템), npm 11.19.0이다. 기존 Node 최소값과 npm 10~11 허용 범위는 유지하고 packageManager만 이번 npm 기준으로 갱신했다. 시스템 Node/npm 설치나 영구 PATH는 변경하지 않았다.
- 패키지: Windows x64 폴더/ASAR을 실제 생성했다. 앱 ASAR 루트가 dist/·electron/·package.json만 포함하고 테스트·문서·node_modules가 없는지 확인했다. 한글·공백 경로의 새 프로젝트에서 npm ci·Electron 준비·테스트·패키징을 재현하고, 앱 폴더만 복사한 독립 실행도 확인했다. 실행 파일 하나가 아니라 Electron 자산·DLL·라이선스를 포함한 폴더 전체를 사용한다.
- 오프라인 조건: 새 테스트 프로필의 패키지를 연결 불가능한 루프백 프록시와 우회 금지 조건으로 시작하고, 캐시/연결을 정리한 후에도 Shell을 로드했다. 별도 메모리 대조 세션은 직접 연결 성공 → 같은 프록시에서 ERR_PROXY_CONNECTION_FAILED를 확인한다. 앱의 요청 허용 목록은 해제하지 않는다. 검사 후 프록시는 테스트 앱 세션에서만 복원한다. [Electron 세션 프록시 API](https://www.electronjs.org/docs/latest/api/session#sessetproxyconfig).
- 검증 방법 선택 이유: 초기 네트워크 에뮬레이션 시도에서 navigator.onLine과 대조 요청이 차단 근거가 되지 못했다. API 호출 성공만으로 통과시키지 않고 실제 연결 실패를 확인할 수 있는 프록시 조건으로 전환했다. OS 전체의 연결·방화벽·프록시 설정은 건드리지 않았다.
- 보안: 실제 CSP의 인라인 스크립트/배포 인라인 스타일 거부, CSP와 독립적인 세션 요청 차단, 알림·위치 권한 거부, 새 창·외부/파일 탐색 차단, 패키지 내 자산 경로 검사를 수행했다. 정상 화면 콘솔과 의도적 거부 시험의 진단을 분리해 기록한다. 탐색 취소는 will-frame-navigate가 먼저 처리할 수 있어 두 이벤트를 관측한다. [Electron 탐색 이벤트](https://www.electronjs.org/docs/latest/api/web-contents#event-will-frame-navigate).
- 한계: 별도 새 Windows/VM, 물리적인 네트워크 어댑터 차단, 모든 하드웨어/디스플레이/접근성 조합을 시험한 것은 아니다. PDF 자산·worker·파일 입력·학습 기능은 아직 없으며 해당 Unit에서 다시 검증한다. 서명·설치 프로그램·공개 배포는 수행하지 않는다.

### ADR-016 — 검증에서 발견한 패키징·시작·개발 서버 오류 수정

- 상태: **채택 — Unit 0.4의 환경 문제 수정**, 2026-08-31. 새로운 PDF/CBT 기능이나 권한은 추가하지 않는다.
- 기존 출력: Packager가 기존 폴더를 건너뛰고 빈 결과/성공 코드로 끝나던 동작을 확인했다. 실행 스크립트에서 먼저 출력 존재를 확인해 한국어 안내와 exit code 1로 중단하며, 반환된 패키지가 정확히 1개인지도 확인한다. 기존 결과를 자동 삭제하거나 덮어쓰지 않는다.
- 다운로드: 고정 Electron npm 패키지에 포함된 체크섬을 Packager에 전달한다. 캐시가 있을 때 체크섬을 위해 다시 네트워크에 의존하지 않으며 파일 검증은 유지한다. 캐시 없는 개발 준비의 다운로드 필요성은 그대로다.
- 필수 빌드 누락: 프로토콜 404여도 초기 탐색이 성공으로 처리되어 일반 창/exit code 0이 나왔다. main에서 dist/index.html 접근 가능 여부를 먼저 확인하도록 수정했다. 누락 시 실제 한국어 오류 대화상자와 exit code 1을 확인했다. 보안 정책을 느슨하게 하거나 오류를 숨기지 않는다.
- 개발 서버: 프로젝트 안의 테스트 프로필을 감시하다 잠긴 파일에서 EBUSY가 발생했다. 또 **/work/** 제외 규칙이 상위 work 폴더까지 일치하여 새 복사본의 index.html을 거부했다. 제외 범위를 프로젝트 내부의 .git/docs/work/.local-data/release 절대 경로에 고정하고 감시/파일 제공에서 함께 제외했다. 앱 소스는 제공하며 내부 문서·작업 자료·패키지의 HTTP 접근은 실제 403으로 거부하는지 확인했다.
- 구조: 요청 허용 판단만 electron/security.js로 추출해 직접 검사할 수 있게 했다. 실제 main에서 같은 함수를 사용하며 허용 목적지·preload API·sandbox 설정은 확대하지 않았다.
- 종료: 실제 개발 명령/패키지에서 창 표시 직후·250ms 후·1500ms 후 종료 코드 0과 포트 해제를 확인했다. 다만 패키지 250ms 종료에서 `GPU state invalid after WaitForGetOffsetInRange` 진단 2줄이 재현됐다. 보강한 검사에서 종료 전 stderr는 비어 있고 닫기 요청 후 진단이 생긴 것을 확인했다. 이후 18회 재검사가 통과해도 간헐 오류가 해결됐다고 볼 수 없다. 원인 미확정이며 그래픽 가속·sandbox·로그를 끄거나 임의 대기 시간을 넣지 않았다. 실제 Ctrl+C에서도 개발 포트가 정리됐다.
- 완료 판단: 정상 화면·보안·오프라인 검사의 성공과 종료 진단을 구분한다. 사용자 원문의 Console Error 없음 및 ROADMAP 오류 없음 기준을 낮추지 않으며 Unit 0.4/Phase 0 완료는 보류한다. PowerShell 검사 자체의 초기 ExitCode 수집 문제는 프로세스 핸들을 미리 보관해 수정했고 Windows 기본 PowerShell 5.1에서 재확인했다.
- 추가 대조: 같은 Electron 바이너리와 Shell 자산을 파일로 여는 작은 시험 창에서 요청 정책·커스텀 프로토콜 없이 39회 종료를 확인했지만 GPU 진단은 재현되지 않았다. 앱 패키지와 로딩 조건이 다르므로 특정 모듈이나 Electron/드라이버 자체를 원인으로 확정할 근거는 부족하다. 제품 코드는 이 대조를 위해 변경하지 않았다.

### ADR-017 — 명시적으로 요청된 Unit 1.1의 범위와 선행 상태

- 상태: **채택 — Unit 1.1 파일 선택 구현·기능 검사 수행**, 2026-09-01. 전체 무오류 완료 판정은 기존 종료 오류 때문에 보류.
- 근거: 사용자가 Unit 0.4 미해결 안내를 받은 뒤 Unit 1.1 진행을 명시적으로 요청했다. 파일 선택에 필요한 작업을 진행하되 Unit 0.4와 Unit 1.0을 소급 완료하거나 후속 Unit 전체의 승인으로 해석하지 않는다.
- 범위: 네이티브 파일 선택, 기본 입력 검사, 이름·크기·상태 표시, 관련 보안·원본 불변 검사. 드롭·파서·본문 표시·페이지·학습·저장은 제외한다. Unit 1.0의 유형별 전체 샘플 행렬도 만들지 않는다.
- 최소 입력 정책: 파일 크기 상한은 50 MiB(52,428,800바이트)로 임시 설정하고 같은 크기는 허용한다. Unit 1.6에서 작은 합성 PDF의 기본 시간 안전 기준은 확인했지만 50 MiB 입력이나 모든 실물 PDF의 렌더링 보장은 아니므로 상한의 임시 성격을 유지한다.
- 완료 판단: 파일 선택 경계 36개, Electron 3경로, 실제 Windows 선택 창 검사는 통과했다. 그러나 기존 GPU 로그가 종료 검사 18회 중 1회 재현됐다. 기능 구현·검사 성공과 Unit 전체 완료를 구분하고 OPEN-09를 유지한다.
- 문서 정정: 이전 DECISIONS에서 GPU 진단과 Phase 5 저장 항목에 OPEN-07이 중복되었다. 저장 항목은 OPEN-07, GPU 진단은 OPEN-09로 분리하고 기존 GPU 참조를 정정한다.

### ADR-018 — 인자 없는 선택 API와 읽기 전용 기본 검사

- 상태: **채택 — Unit 1.1 구현·기능 검사 통과**, 2026-09-01. 당시 preload에는 selectPdfFile() 하나만 추가했고 Unit 1.2의 좁은 드롭 API는 ADR-019에서 확장했다.
- IPC: renderer에서 경로·필터·IPC 채널을 받지 않는다. main은 소유 창의 webContents, mainFrame 객체, 정확한 renderer URL과 인자 없음 조건을 검사한다. 같은 주소를 연 다른 창의 실제 요청도 거부했다. [Electron IPC 발신자 검증](https://www.electronjs.org/docs/latest/tutorial/security#17-validate-the-sender-of-all-ipc-messages).
- 선택 창: 소유 창에 연결한 비동기 showOpenDialog로 PDF 한 개만 선택하고 dontAddToRecent를 사용한다. 앱은 최근 목록·파일 경로를 따로 저장하지 않는다. Windows 자체의 대화상자 기록까지 제거하는 기능은 아니다. [Electron 파일 선택 API](https://www.electronjs.org/docs/latest/api/dialog#dialogshowopendialogwindow-options).
- 읽기: 일반 절대 Windows 경로와 .pdf 확장자를 확인한다. UNC·장치·상대 경로·대체 데이터 스트림·예약 장치 이름을 거부하며 실제 경로로 해석한 결과도 검사한다. 선택한 파일을 r 모드로 열고 같은 핸들에서 파일 여부·크기·앞 9바이트를 읽은 뒤 닫는다. 취소·중복·불신 IPC는 읽기를 시작하지 않는다.
- 서명: 첫 줄의 %PDF-1.0~1.7 또는 %PDF-2.0 뒤 CR/LF만 허용한다. 8비트 값을 보존해 검사하고 짧은 읽기를 처리한다. 앞에 다른 데이터가 붙은 비표준 파일은 수용하지 않는다. 기본 서명 통과가 구조 유효성·암호 없음·렌더링 가능을 보장하지 않는다. 파서로 손상/암호를 판정하는 일은 Unit 1.3이다.
- 결과: 이름·바이트 크기만 반환하고 원본 경로·본문·파일 핸들은 renderer에 제공하거나 이후용으로 보관하지 않는다. 파일 전체 읽기와 PDF 객체·페이지 수·documentId를 선행 구현하지 않는다. 이후 실제 렌더링 연결 시 승인된 파일의 읽기와 교체/정리 계약을 확장해야 한다.
- 상태: 선택/검사 중에는 버튼과 main 선택기를 중복 실행하지 않는다. 소유 창/프레임이 사라지거나 바뀐 뒤 도착한 선택 결과는 읽지 않는다. 성공 시 화면 메타데이터를 교체하고 취소·실패 시 이전 선택을 유지한다. 오류 코드는 한국어 상태 안내로 처리하며 개인 경로가 든 예외 메시지를 로그나 UI에 노출하지 않는다.
- UI: 파일명은 textContent로 표시하고 본문 미지원·손상/암호 미확인 상태를 명시한다. 크기는 작은 파일이 0 MiB처럼 보이지 않도록 바이트/KiB/MiB로 표시한다. 키보드 포커스와 role=status·aria-busy를 사용하며 선택은 새로고침/종료 시 초기화된다.
- 경계/한계: 현재 검사는 선택 시점의 메타데이터다. 파일 감시·강한 변경 잠금은 없다. 매핑 드라이브나 클라우드 자리표시자의 실제 저장 매체 판별까지 구현하지 않았으며 로컬 디스크 시험만 수행했다. 파일 경로 허용 목록 검사만으로 모든 네트워크 저장소 접근을 차단했다고 주장하지 않는다.
- 검증: 실제 파일의 해시·수정 시각, 잘못된 서명·고비트 서명·빈 파일·크기 경계·핸들 정리·실패 재시도·다른 창 발신자를 확인했다. 패키지에서는 생성한 시험 파일의 읽기 권한만 일시 거부하고 정확히 복원해 실제 접근 거부 안내와 복원 후 동일 해시를 확인했다. 개인 파일 권한은 변경하지 않았다.
- 도구 구분: Electron 3경로 검사는 native dialog 결과를 제어하지만 IPC·파일 읽기·UI는 실제로 실행한다. test:native는 별도로 실제 Windows 대화상자의 선택·취소를 확인한다. UI 자동화 패턴이 없는 기본 컨트롤은 해당 앱 소유 대화상자 안에서 확인한 핸들만 사용한다. 테스트의 디버그 연결·권한 fixture·UI 제어는 제품 패키지에 포함하지 않는다.

### ADR-019 — 실제 File 기반 드롭과 파일 선택 검사 경로 공유

- 상태: **채택 — Unit 1.2 구현·기능 검사 통과**, 2026-09-01. 전체 무오류 완료 판정은 OPEN-09 때문에 보류.
- 범위: Windows 탐색기의 로컬 PDF 한 파일 드롭, 드롭 상태 표시와 한국어 결과 안내만 추가한다. 다중 파일 일괄 처리·폴더 탐색·URL 다운로드·PDF 파싱/렌더링·저장은 구현하지 않는다.
- 경로 경계: 폐기된 File.path에 의존하지 않고 sandbox preload의 Electron `webUtils.getPathForFile(file)`을 사용한다. renderer는 실제 File 객체 배열만 전달하고 preload가 얻은 경로는 고정 IPC로 즉시 main에 보내며 renderer에 반환하지 않는다. 메모리에서 생성해 디스크 경로가 없는 File은 빈 경로로 거절한다. [Electron webUtils](https://www.electronjs.org/docs/latest/api/web-utils).
- IPC: main은 선택과 별도의 고정 채널에서도 소유 webContents·mainFrame 객체·정확한 URL·인자 개수와 배열/문자열을 검사한다. raw ipcRenderer·범용 경로 입력·파일 읽기 API는 노출하지 않는다. 다른 창/프레임, 잘못된 인자와 늦게 완료된 요청은 결과를 적용하지 않는다.
- 동일 검사: 한 파일의 드롭 경로는 Unit 1.1의 `inspectPdfFile`에 연결한다. 일반 로컬 경로·확장자·실제 경로·파일 여부·50 MiB·첫 줄 서명·읽기 전용 핸들·변경 감지를 그대로 적용하고 이름/크기만 반환한다. 폴더는 같은 검사에서 NOT_A_FILE로 거절한다.
- 거절 정책: renderer는 파일이 없는 URL 드롭과 빈 전송, 다중 드롭을 읽기 전에 거절한다. main도 빈 배열·다중 경로·빈 경로를 별도로 거절한다. 실패·취소는 직전 성공 정보를 유지하며 개인 경로나 예외 메시지를 표시하지 않는다.
- 순서: 파일 선택과 드롭은 main의 같은 실행 잠금과 UI의 같은 진행 상태를 공유한다. 선택 창이 늦게 끝나거나 드롭 검사가 겹쳐 이전 요청이 최신 화면을 덮지 않는다.
- UI/접근성: 문서 작업 공간에 드롭 안내와 시각적 drag-over 상태를 추가한다. 상태는 role=status 문구로도 전달하고 기존 PDF 선택 버튼을 키보드 대안으로 유지한다. 브라우저 기본 드롭 탐색은 막지만 앱의 기존 탐색/새 창 제한을 완화하지 않는다.
- 검증: 경계 검사 43개와 Electron 개발·빌드·패키지 3경로에서 실제 디스크 파일 drag event, 다중 파일·폴더·URL·빈 경로·빈 전송, 원본 해시·이전 선택 유지·발신자·입력 경쟁을 확인했다. 실제 Windows 선택 창 회귀도 통과했다. GUI 검사는 사용자 Windows 실행 환경에서 수행했으며 제품의 GPU·sandbox·네트워크 설정은 변경하지 않았다.
- 제한: Windows 탐색기 기반 로컬 파일만 검증했다. 브라우저/메일의 가상 항목, shell namespace, 클라우드 자리표시자·매핑 드라이브의 실제 저장 매체 판별은 보장하지 않는다. 파일 감시·PDF 구조 판정·본문 표시와 열린 문서 핸들 수명은 후속 Unit 범위다.

### ADR-020 — 로컬 PDF.js 자산과 첫 페이지 렌더 수명

- 상태: **채택 — Unit 1.3 구현·기능 검사 통과**, 2026-09-01. 전체 무오류 완료 판정은 OPEN-09 때문에 보류.
- 범위: 선택·드롭으로 승인된 한 PDF의 첫 페이지만 Canvas에 표시하고 전체 페이지 수, 암호 필요, 손상/지원 불가 상태를 안내한다. 페이지 이동·확대·축소·너비 맞춤·Text Layer·링크/양식 실행·분석·CBT는 구현하지 않는다.
- 버전: 공식 npm 배포 메타데이터의 Node 요구사항을 현재 Node 24 범위와 대조해 `pdfjs-dist` 6.3.289를 정확히 고정했다. PDF.js 본체·worker·CMap·ICC·표준 글꼴·WASM은 한 패키지 버전에서 가져온다. 직접 의존성은 package.json, 전체 전이 의존성은 lockfile로 고정한다.
- 파일 경계: Unit 1.1/1.2의 확장자·일반 로컬 경로·실제 경로·파일 여부·50 MiB·첫 줄 서명 검사를 유지한다. 승인된 파일은 같은 `r` 핸들에서 전체 바이트를 읽고 읽기 전후 크기·수정 시각을 다시 확인한다. renderer에는 이름·크기·바이트만 전달하며 경로·쓰기·범용 파일 API는 제공하지 않는다. 바이트와 PDF.js 객체는 현재 화면 메모리에만 있고 교체·새로고침·종료 시 정리한다.
- 어댑터: PDF.js 객체는 `src/pdf/` 밖으로 내보내지 않는다. 문서 요청 식별자와 현재 작업 레코드로 늦은 결과를 무시하고 새 파일·종료 시 loading/render task와 document를 취소·파기한다. 현재는 `getPage(1)`과 scale 1 viewport만 사용하고 Canvas backing size에는 디스플레이 픽셀 비율을 반영한다. 사용자 배율 정책과 Canvas 자원 상한은 Unit 1.5/1.6에서 결정한다.
- 로컬 자산: Vite 설정이 설치된 `pdfjs-dist`에서 CMap·ICC·표준 글꼴·WASM·라이선스를 생성 전용 public 작업 폴더로 복사한 뒤 `dist/pdfjs/`에 포함한다. worker는 Vite가 별도 로컬 모듈로 출력한다. 개발은 루프백 origin, 빌드·패키지는 `local-cbt://app/`만 사용하며 CDN·원격 글꼴·원격 worker는 없다.
- CSP/프로토콜: worker와 내부 자산 fetch를 위해 배포 CSP의 `worker-src`와 `connect-src`를 `'self'`로 명시했다. 이는 외부 연결 허용이 아니다. Electron 세션 요청 허용 목록은 계속 정확한 `local-cbt://app`만 허용하고, 로컬 프로토콜도 `.mjs/.bcmap/.icc/.pfb/.ttf/.wasm`만 기존 경로 정규화·host·GET 검사 뒤 제공한다.
- 실패 상태: 암호 입력 기능을 만들지 않는다. PDF.js가 암호를 요구하면 지원하지 않는다는 안내를 표시하고 암호 해제 복사본을 요청한다. 구조 손상/지원 불가는 별도 안내로 처리한다. 새 파일이 파서 단계에서 실패하면 이전 Canvas를 숨겨 이전 문서를 현재 파일로 오인하지 않게 하며, 기본 입력 자체가 실패/취소하면 직전 성공 문서를 유지한다. 예상된 손상 파서 경고는 PDF.js verbosity를 오류 수준으로 제한해 정상 Console 경고로 남기지 않는다.
- 검증: 한글 글꼴 subset과 포함 raster 이미지를 가진 재배포 가능한 합성 PDF, 그 암호화 복사본, 구조가 잘린 합성 입력을 사용했다. Poppler 렌더를 눈으로 확인하고, Electron 개발·빌드·패키지에서 실제 Canvas 유색 픽셀·페이지 수·worker 요청·암호/손상 상태·이전 Canvas 숨김·원본 해시를 확인했다. 패키지는 연결 불가 프록시에서도 첫 페이지와 내부 자산을 표시했고 CMap·ICC·표준 글꼴·WASM URL을 직접 검사했다.
- 완료 판단: Node 검사 47개, Electron 3경로, 실제 Windows 선택 창 1개는 통과했다. 종료 검사 18개 중 기존 개발 모드 즉시 종료 GPU 진단 2개가 재현되어 Unit 0.4와 전체 무오류 완료는 계속 보류한다. 이 실패를 PDF 렌더 기능 실패로 합치거나 숨기지 않는다.
- 한계: 합성 한 페이지로 한글·이미지 경로를 확인했으며 임의의 실제 출판 PDF 호환성을 보장하지 않는다. 암호 해제, 다중 페이지 탐색, 고유 회전의 다양한 실물 검증, 큰 이미지/복잡한 글꼴 성능·메모리 예산, 파일 감시는 후속 범위다.

### ADR-021 — 1부터 시작하는 페이지 상태와 최신 렌더 우선

- 상태: **채택 — Unit 1.4 구현·기능 검사 통과**, 2026-09-01. 전체 무오류 완료 판정은 OPEN-09 때문에 보류.
- 범위: 현재 열린 PDF에서 처음·이전·번호 입력·다음·마지막 페이지로 이동한다. 확대·축소·너비 맞춤·사용자 회전·Text Layer·분석·CBT·저장은 추가하지 않는다.
- 번호 계약: UI와 어댑터의 공개 페이지 번호는 모두 1부터 시작한다. 입력은 현재 전체 페이지 수 안의 안전한 정수만 허용한다. 0, 전체 페이지 수 초과, 소수와 빈 값은 `INVALID_PAGE_NUMBER`로 거부하고 Canvas·현재 페이지를 유지한다. 경계에서는 이동 버튼을 비활성화한다.
- 렌더 수명: 열린 PDF document는 유지하되 현재 한 페이지의 Canvas만 렌더한다. 문서 요청 식별자와 별도의 페이지 렌더 요청 식별자를 사용한다. 새 페이지 요청은 진행 중인 이전 render task를 취소하고, getPage 또는 render 결과가 늦게 도착해도 최신 식별자와 현재 document가 모두 일치할 때만 화면 상태를 갱신한다. 잘못된 번호 요청도 직전 진행 중 렌더를 무효화해 이후 늦은 결과가 현재 페이지를 바꾸지 못하게 한다.
- UI 상태: 연속 이동 중 버튼 계산은 마지막으로 요청한 페이지를 기준으로 하므로 빠른 다음 클릭이 같은 페이지를 반복 요청하지 않는다. 렌더가 끝나면 번호 입력·상태 패널·접근성 이름을 한 결과로 갱신하고 페이지 스크롤을 좌상단으로 돌린다. 번호 입력은 브라우저 기본 오류 팝업 대신 한국어 `role=status` 안내를 사용한다.
- 파일 교체: 새로 선택하거나 드롭한 PDF는 이전 페이지 렌더와 document를 취소·파기하고 항상 1페이지부터 연다. 입력 자체의 실패·취소는 Unit 1.1/1.2 계약대로 직전 성공 문서를 유지하고, 새 파일의 암호·손상 판정은 Unit 1.3 계약대로 이전 Canvas를 숨긴다.
- 검증: 어댑터 검사에서 첫·마지막·0·초과·소수·문서 없음, 진행 중 렌더 취소와 최신 결과를 확인했다. 개발·빌드·패키지 Electron 검사에서는 서로 다른 색의 5페이지 합성 PDF로 처음/마지막/이전, 0·6·1.5 거부와 픽셀 유지, 빠른 다음 3회 후 4페이지, 단일 페이지 파일 교체 후 1/1 초기화를 확인했다. 원본 해시와 정상 Console 상태도 유지했다.
- 완료 판단: Node 검사 48개, Electron 3경로, 실제 Windows 선택 창 1개는 통과했다. 종료 검사 18개 중 기존 개발 모드 즉시 종료 GPU 진단 2개가 재현되어 Unit 0.4와 전체 무오류 완료는 계속 보류한다.
- 한계: 합성 5페이지의 기본 방향·작은 vector 내용으로 이동을 확인했다. 고유 회전·배율·Canvas 픽셀 예산과 배율 중 이동은 Unit 1.5의 ADR-022에서 후속 결정했다. 서로 다른 복잡도·대형 문서의 전체 성능은 Unit 1.6 범위다. 키보드 단축키나 페이지 썸네일은 이번 범위에 없다.

### ADR-022 — 제한된 배율·너비 맞춤과 Viewer 조작 배치

- 상태: **채택 — Unit 1.5 구현·기능 검증 통과**, 2026-09-01. 최종 종료 반복은 15/18이며 OPEN-09 재현으로 전체 완료를 보류한다. 너비 맞춤과 하단 도구 배치는 Unit 1.6의 ADR-023이 대체하며, 나머지 배율·자원·렌더·상태 계약은 유지한다.
- 범위: 현재 한 페이지 Canvas에 50·75·100·125·150·175·200% 배율과 페이지별 너비 맞춤을 제공한다. PDF 고유 회전은 PDF.js viewport가 반영하지만 사용자 회전 버튼, Text Layer, 링크·양식, 분석, CBT, 저장은 추가하지 않는다.
- 배율·창 계약: 새 문서는 100%에서 시작한다. 너비 맞춤은 현재 페이지의 scale 1 viewport 폭과 PDF 스크롤 영역의 실제 CSS 폭으로 계산하고 50–200% 안으로 제한한다. `ResizeObserver`에서 창/영역 폭 변화를 짧게 모아 같은 현재 페이지를 다시 렌더한다. 고정 배율 버튼을 누르면 너비 맞춤 모드를 해제한다.
- DPI·자원 계약: Canvas CSS 폭·높이는 선택한 viewport 배율을 유지하고 backing bitmap만 디스플레이 픽셀 비율에 맞춘다. 이름 있는 상한 `MAX_CANVAS_PIXELS=16,777,216`, `MAX_CANVAS_DIMENSION=8,192`를 넘지 않도록 backing pixel ratio를 낮춘다. 제한 여부를 Canvas/도구 상태에 남기되 화면 배율을 몰래 바꾸지 않는다. 모든 페이지나 배율 결과를 캐시하지 않고 현재 Canvas 하나만 유지한다.
- 렌더 수명: 페이지·확대·축소·너비 맞춤·창 크기 재렌더는 ADR-021의 같은 렌더 요청 식별자와 cancel 경로를 사용한다. 늦은 page/render 결과는 현재 문서와 최신 요청이 모두 일치할 때만 Canvas·페이지·배율 상태를 갱신한다.
- Viewer 배치: IDEA-029를 이번 Unit에 채택했다. 페이지 번호 도구와 배율 도구를 PDF 표시 영역 아래에 두고, 같은 페이지 상태를 공유하는 이전·다음 보조 버튼을 PDF 좌우에 둔다. 40rem 이하에서는 좌우 보조 버튼을 숨기고 하단 이동 도구를 유지해 PDF와 향후 overlay를 가리지 않는다.
- 상태 안내: 정상 렌더 때마다 표시하던 `n페이지를 표시했습니다. 전체 nn페이지입니다.` 행은 제거한다. 로딩·오류·잘못된 번호의 `role=status`는 Viewer 상단에 유지한다. 정상 파일 성공은 footer의 별도 `role=status`에서 `PDF를 열었습니다. 원본 파일은 변경하지 않았습니다.`로 알리고 기존 Local First 안내도 함께 유지한다.
- 검증: Node 49개에서 배율 경계·fit width·고유 회전·최신 배율 우선·Canvas 상한을 검사했다. 개발·빌드·패키지 Electron 3경로에서 좌우/하단 이동 상태, 50/200% 경계, 빠른 배율 요청, 기본/최소 창 너비 맞춤 재계산, 작은 창 가로 넘침 없음, 고유 90도 회전, footer·숨긴 중복 상태, 오프라인·보안·원본 해시를 확인했다. 실제 Windows 선택 창 1개도 통과했다. 최종 종료 반복은 개발 모드 즉시 종료 3회에서 기존 GPU 진단이 재현되어 15/18이며, 패키지 9/9와 모든 종료 코드·포트 정리는 정상이다.
- 한계: PDF.js가 허용하는 모든 페이지 크기·고유 회전·`userUnit`·복잡한 이미지/글꼴 조합과 실제 Windows 디스플레이 배율별 성능을 보장하지 않는다. 50 MiB 입력 상한은 렌더 시간 보장이 아니다. 후속 Unit 1.6의 ADR-023에서 작은 합성 PDF의 기본 시간 안전 기준과 통합 경로를 확인했지만 실물별 파서·캐시·시간 예산은 남아 있다. 키보드 배율 단축키·핀치·사용자 회전·썸네일은 이번 범위가 아니다.

### ADR-023 — 오른쪽 Viewer 제어와 높이 맞춤·PDF 기초 통합 검증

- 상태: **채택 — Unit 1.6 구현·통합 검증 통과**, 2026-09-01. 최종 종료 반복은 17/18이며 OPEN-09 재현으로 전체 완료를 보류한다.
- 범위와 우선순위: 사용자가 검토했던 아이디어를 신규 Unit 1.6으로 추가하도록 명시했다. ADR-022의 페이지/배율 도구 하단 배치와 너비 맞춤만 대체한다. 50–200% 단계 배율, 좌우 보조 이동, PDF 고유 회전, Canvas/DPI 상한, footer 성공 안내와 최신 렌더 우선 계약은 유지한다. Text Layer·사용자 회전·분석·CBT·저장은 추가하지 않는다.
- Viewer 배치: 56rem 초과 기본 창에서는 앱 상태 카드 아래의 오른쪽 사이드 카드에 페이지 번호, 처음·이전·다음·마지막, 축소·현재 배율·확대·높이 맞춤을 둔다. PDF 좌우 보조 버튼은 같은 페이지 상태를 공유한다. 56rem 이하 한 열에서는 제어 카드를 PDF 아래이면서 앱 상태 카드보다 앞에 두고, 40rem 이하에서는 좌우 보조 버튼만 숨긴다. 제어 카드가 문서 폭을 넘지 않는지 1120×760과 640×480에서 확인한다.
- 높이 맞춤 계약: 현재 페이지의 scale 1 viewport 높이와 `.pdf-page-scroll`의 실제 `clientHeight`에서 상하 padding을 뺀 값을 사용한다. 결과는 기존 50–200% 배율 경계로 제한한다. `ResizeObserver`에서 세로 가용 공간 변화를 120ms로 모아 현재 페이지를 다시 렌더하고, 고정 확대·축소를 누르면 높이 맞춤 모드를 해제한다. 최소 창이나 매우 긴 페이지에서 계산값이 50%보다 작으면 50%와 세로 스크롤을 유지한다.
- 수명·자원: 페이지 이동·고정 배율·높이 맞춤·창 크기 재렌더는 ADR-021/022의 같은 요청 식별자와 cancel 경로를 사용한다. 현재 Canvas 하나만 유지하고 문서 교체·새로고침·종료에서 이전 PDF document/render task를 정리한다. backing bitmap 상한 16,777,216픽셀·한 변 8,192픽셀과 50 MiB 입력 상한은 바꾸지 않는다.
- 통합 검증: 버전 0.1.6 Windows x64/ASAR 패키지에서 앱 전용 연결 불가 프록시 아래 PDF 표시와 번들 worker·CMap·ICC·표준 글꼴·WASM 접근을 확인했다. 누락·허용 외·경로 변형 자산은 기존 400/403/404 계약으로 거부된다. 파일 선택·드롭·교체·새로고침, 암호·손상, 원본 해시, 읽기 권한 거부, 정상 Console과 보안 거부 경로를 개발·빌드·패키지에서 다시 확인했다.
- 기본 시간 증거: 같은 작은 합성 문서와 현재 PC에서 10초를 회귀 안전 기준으로 두었다. 개발/빌드/패키지 순서로 첫 페이지 372/228/144ms, 높이 맞춤 27/28/24ms, 마지막 페이지 49/45/49ms였다. 이는 테스트 중 멈춤을 찾는 보수적 기준이며 50 MiB 입력, 복잡한 실물 PDF, 다른 PC나 디스플레이 배율의 성능 보장이 아니다. 별도 페이지 캐시는 도입하지 않는다.
- 완료 판단: 형식 검사, Node 49개, 빌드·패키지, Electron 3경로, 실제 Windows 선택 창 1개는 통과했다. 종료 반복은 개발 모드 즉시 종료 1회에서 기존 GPU 진단이 재현되어 17/18이었다. 패키지 9/9, 개발 250ms·1500ms 6/6, 모든 종료 코드 0과 포트 해제는 정상이다. OPEN-09를 숨기거나 그래픽·보안 설정을 낮추지 않는다.
- 한계: Unit 1.0의 전체 샘플 행렬은 미착수다. 모든 실제 PDF의 자원 사용·파서 시간·렌더 시간과 캐시 정책을 확정하지 않았고, 실제 다중 모니터·여러 Windows 디스플레이 배율·스크린 리더 검증도 남아 있다. Phase 2 기능은 이번 결정에 포함되지 않는다.

### ADR-024 — Phase 2 텍스트 분석 경계와 실패 정책

- 상태: **채택 — Unit 2.0 구조 검토 완료**, 2026-09-01. 문서 결정이며 앱 코드는 버전 0.1.6 그대로다.
- 현재 구조 판단: PDF.js document/page/TextContent 객체는 이미 PDF 어댑터 안에 격리돼 있어 기존 렌더 경계를 확장할 수 있다. `src/analysis/`는 아직 없으며 Unit 2.1에서 실제 책임이 생길 때만 만든다. 빈 폴더·추상 service·DB·IPC를 미리 추가하지 않는다.
- 추출 경계: Unit 2.1에서 PDF 어댑터에 현재 문서의 한 페이지를 받는 `extractPageText({ pageNumber })`를 추가한다. PDF.js 6.3.289의 `getTextContent({ includeMarkedContent: false, disableNormalization: false })`를 사용하고 원래 항목 순서를 보존한다. 전체 페이지 선행 추출·OCR·Text Layer DOM 읽기·키워드 검색은 하지 않는다. 추출 실패는 Canvas 원문 Viewer를 닫거나 실패 상태로 바꾸지 않는다.
- 데이터 경계: 어댑터는 PDF.js 객체 대신 `PageTextSource v1` 순수 데이터를 반환한다. 필수 필드는 `contractVersion`, 세션 `documentRevision`, 1부터 시작하는 `pageNumber/pageCount`, `language`, page `viewBox/userUnit/rotation`, 텍스트 item의 `sourceIndex/sourceText/direction/transform[6]/width/height/fontName/hasEOL`이다. font style은 임의 fontName을 객체 key로 쓰지 않고 `fontName/ascent/descent/vertical/fontFamily`의 배열로 복사한다. 값은 새 배열·객체로 복사하고 유한한 숫자·문자열·불리언·null만 허용한다. 경로·파일 바이트·PDF.js prototype 객체는 포함하지 않는다. 형식이 잘못된 TextContent를 부분 정상화하지 않고 `INVALID_TEXT_SOURCE`로 보류한다.
- 분석 경계: Unit 2.1의 순수 분석 함수는 PageTextSource 또는 현재 문서의 추출 실패 결과에서 `PageTextAssessment v1`을 만든다. 결과는 `documentRevision`, `pageNumber`, `quality`, `reasonCodes[]`, 이름 있는 `metrics`, 진단용 `plainText`를 포함한다. plainText는 sourceText를 원래 순서로 연결하고 `hasEOL` 뒤에만 줄바꿈을 넣는다. 추정 공백·줄/문단 복원·검색용 정규화는 수행하지 않으며 sourceIndex를 근거로 유지한다. 추출 실패나 잘못된 source에서는 unknown과 빈 plainText를 반환한다. 문서 없음·잘못된 페이지·canceled 결과에는 assessment를 만들지 않는다.
- 품질 상태: `text-usable`은 현재 텍스트 분석 입력으로 쓸 근거가 있다는 뜻일 뿐 CBT 지원이나 올바른 읽기 순서를 뜻하지 않는다. `text-insufficient`는 추출 성공 후 빈 항목·공백뿐·페이지 번호 수준·문자량/품질 부족 같은 명시적 근거가 있는 정상 결과다. `unknown`은 추출 실패, 잘못된 source, 상충 신호 또는 현재 근거로 판정할 수 없는 상태다. 후자의 두 상태에서는 자동 분석을 보류한다. 텍스트 없음이나 이미지 존재만으로 스캔이라고 단정하지 않는다.
- reason code: 최소 후보를 `NO_TEXT_ITEMS`, `WHITESPACE_ONLY`, `TOO_LITTLE_TEXT`, `LOW_TEXT_QUALITY`, `INVALID_TEXT_SOURCE`, `CONFLICTING_SIGNALS`, `TEXT_EXTRACTION_FAILED`로 정한다. Unit 2.1에서 한글 분절·빈/이미지 위주·혼합·페이지 번호 수준·비정상 문자열 고정 샘플을 측정한 뒤 실제 사용 코드와 숫자 임계값을 이름 있는 상수로 확정한다. 샘플 없이 문자 수·비율을 결정하지 않는다.
- 수명과 취소: 새 document open 시도가 시작되거나 dispose될 때 파일명·경로·해시와 무관한 세션 한정 `documentRevision`을 증가시킨다. 성공한 현재 document record가 그 revision을 소유하며 실패한 새 open도 이전 revision을 무효화한다. `getTextContent()` Promise를 즉시 중단할 수 없더라도 늦은 결과는 documentRevision과 추출 request id가 모두 최신일 때만 채택한다. 현재 페이지 표시용 상태와 페이지별 분석 상태를 섞지 않는다. 캐시를 도입하지 않고 현재 세션 메모리만 사용한다.
- 페이지/문제 구분: PageTextSource와 PageTextAssessment는 PDF page 자료다. `questionId`, 정답, 해설, Region, 지원 여부를 만들지 않으며 pageNumber를 questionId로 사용하지 않는다. TextItemRecord bbox는 Unit 2.2, Debug Overlay는 2.5, 키워드는 2.3, 영역은 2.4, 지원 판정은 2.6, Question/CBT는 이후 Unit의 책임이다.
- 개인정보와 UI: 원문 텍스트·경로를 Console, 자동 결과 JSON, 외부 서비스에 기록하지 않는다. 일반 UI에는 원문 추출 덤프를 표시하지 않고 진행·품질·공개 실패 요약만 전달한다. Debug Overlay는 Unit 2.5에서 일반 사용 경로와 분리한다. 파일 교체·새로고침·종료 때 텍스트와 평가 결과를 폐기한다.
- 검증 계획: Unit 2.1에서 어댑터 성공/문서 없음/잘못된 페이지/추출 예외/논리 취소, 순수 분류의 세 상태와 reason code, 한글 분절·혼합 샘플, 경로·PDF.js 객체 비노출, 원본 해시, 기존 Viewer 회귀를 검사한다. Unit 2.2에서 raw transform/style/page metadata를 회전 전 PDF user space bbox로 바꾸고 회전·DPI·확대와 대조한다. Unit 2.5에서 sourceIndex-bbox를 화면으로 대조한 뒤 2.3~2.6 의미 분석을 각각 검증한다.
- 제외 범위: 실제 추출·분류 코드, 품질 숫자, 좌표 계산, Text Layer, Debug Overlay, 키워드·영역·정답, 마스크, CBT, 영구 저장, OCR/AI는 Unit 2.0에 포함하지 않는다. Unit 1.0과 OPEN-09 상태도 바꾸지 않는다.

### ADR-025 — Unit 2.1 현재 페이지 텍스트 추출과 품질 기준

- 상태: **채택 — Unit 2.1 구현·검증 완료**, 2026-09-02. 앱과 Windows x64/ASAR 패키지는 버전 0.2.1이다.
- 추출 구현: PDF 어댑터의 `extractPageText({ pageNumber })`는 현재 문서의 유효한 페이지 한 개에만 `getTextContent({ includeMarkedContent: false, disableNormalization: false })`를 호출한다. 성공 결과는 `status: extracted`와 PageTextSource v1이고, 문서 없음·잘못된 페이지·논리 취소·추출 실패·잘못된 TextContent는 원문 예외 없이 안정된 공개 코드로 반환한다. 전체 문서 선행 추출이나 페이지 캐시는 없다.
- 복사·검증: sourceIndex와 sourceText 순서를 유지하고 direction·transform[6]·width·height·fontName·hasEOL, page viewBox·userUnit·rotation, 실제 참조 font style만 새 객체·배열로 복사한다. Text Item·page metadata와 fontFamily가 잘못되거나 font metric이 문자열·무한대이면 부분 복구하지 않고 `INVALID_TEXT_SOURCE`로 보류한다. PDF.js가 font ascent/descent를 생략·`NaN`으로 주는 경우만 0으로, vertical을 생략한 경우만 같은 font의 `ttb` direction 여부로 정규화한다. 결과에는 경로·파일 바이트·PDF.js 객체·임의 style key가 없다.
- 품질 상수: 한글 분절, 빈/벡터·이미지 위주, 혼합, 페이지 번호 수준, replacement character 고정 샘플과 설치된 PDF.js 6.3.289의 한글+이미지 fixture를 근거로 `MIN_USABLE_NON_WHITESPACE_CHARACTERS = 12`, `MIN_READABLE_CHARACTER_RATIO = 0.8`을 채택한다. 실제 fixture는 6개 item·비공백 73자·판독 가능 비율 1이었다. 이 기준은 후속 분석 입력 보류선이며 정확도·CBT 지원 확률이 아니다.
- 분류 규칙: 항목 없음은 `text-insufficient / NO_TEXT_ITEMS`, 공백뿐이면 `WHITESPACE_ONLY`, 12자 미만이면 `TOO_LITTLE_TEXT`, 판독 가능 비율 0.8 미만이면 `LOW_TEXT_QUALITY`다. 판독 가능 문자가 12개 이상인데 품질 비율은 낮은 상충 결과만 `unknown / CONFLICTING_SIGNALS`로 둔다. 잘못된 source와 추출 실패도 각각 `unknown`이고 canceled·문서 없음·잘못된 페이지에는 assessment를 만들지 않는다.
- 수명·정리: documentRevision은 open 시도와 dispose에서 증가하고 별도 text request id가 빠른 추출을 구분한다. 늦은 결과는 두 값이 모두 최신일 때만 채택한다. PDF.js 6.3.289가 자원 해제를 `PDFDocumentLoadingTask.destroy()`에 제공하고 PDFDocumentProxy에는 destroy를 제공하지 않음을 실제 타입·fixture로 확인해 loading task를 정리 주체로 사용한다. 텍스트 실패는 Canvas 상태를 바꾸지 않는다.
- UI·개인정보: 페이지 표시가 바뀔 때만 품질을 다시 확인하고 같은 페이지의 배율·높이 맞춤 재렌더에서는 재추출하지 않는다. UI에는 `텍스트 분석 가능`, `분석 보류`, `확인 불가`의 공개 문구와 reason code 상태만 두며 plainText와 PDF 원문을 DOM·Console·자동 결과 JSON에 기록하지 않는다. 문서 교체·새로고침·종료에서 상태와 추출을 무효화한다.
- 검증: 형식, Node 60개, 실제 PDF.js 한글+이미지 추출·원본 SHA-256, 빌드·Windows x64/ASAR 패키지, 개발·빌드·패키지 Electron 3경로, 실제 Windows 선택 창 검사가 통과했다. 종료 반복은 개발 9/9·패키지 8/9이며 패키지 250ms 1회에서 OPEN-09 GPU 진단이 재현됐다. 18회 모두 창 종료·종료 코드 0·포트 해제는 정상이다.
- 제외 범위: PDF user space bbox, Text Layer, Debug Overlay, 줄/블록, 키워드, 해설·정답 영역, 지원 판정, Question·CBT, 저장, OCR/AI는 Unit 2.1에 포함하지 않는다. 품질이 text-usable이어도 올바른 읽기 순서나 CBT 지원을 의미하지 않는다.

### ADR-026 — Unit 2.2 PDF user space bbox와 viewport 변환

- 상태: **채택 — Unit 2.2 구현·검증 완료**, 2026-09-02. 앱과 Windows x64/ASAR 패키지는 버전 0.2.2다.
- 데이터 계약: PageTextSource v1은 변경하지 않는다. 순수 `createPageTextCoordinates()`가 `PageTextCoordinates v1`을 만들며 결과는 session `documentRevision`, 1부터 시작하는 pageNumber, `coordinateSpace: pdf-user-space`, 복사한 viewBox/userUnit/rotation과 TextItemRecord 배열을 가진다. 각 record는 `sourceIndex`, `text`, bbox의 최소 `x/y`, 크기 `width/height`, `page`만 포함하고 raw transform·font 정보는 PageTextSource에 남긴다.
- bbox 계산: 가로쓰기는 transform의 기준선 축과 item width, 글꼴 축과 style ascent/descent로 네 모서리를 만든다. 회전·반사·비직교 transform도 네 모서리의 축 정렬 최소/최대 bbox로 근사한다. 세로쓰기는 transform의 교차축과 반대 진행축을 사용한 보수적 근사값을 만든다. ascent/descent가 모두 0인 경우에만 PDF.js Text Layer의 초기 ascent와 한 em 높이에 맞춘 이름 있는 기본값 0.8/-0.2를 사용한다.
- 실패 정책: PageTextSource 계약이 다르면 `INVALID_TEXT_SOURCE`, 유효하지 않은 viewBox나 90도 단위가 아닌 고유 회전은 `UNSUPPORTED_PAGE_GEOMETRY`, font metric 역전은 `UNSUPPORTED_FONT_METRICS`, 퇴화 transform·음수 크기는 `UNSUPPORTED_TEXT_GEOMETRY`다. 항목 일부만 정상으로 반환하지 않고 페이지 좌표 분석 전체를 보류한다. 빈 TextContent는 정상적인 빈 좌표 배열이다.
- 화면 투영: `createViewportGeometry()`는 설치된 PDF.js 6.3.289 PageViewport의 viewBox 오프셋·`userUnit`·0/90/180/270도·scale 규칙과 같은 순수 transform/크기를 만든다. PDF point ↔ viewport point 왕복과 PDF bbox → viewport CSS bbox를 제공한다. Canvas device pixel ratio와 backing bitmap은 좌표 API에 포함하지 않아 확대와 DPI를 분리한다.
- 런타임·개인정보: `text-usable`인 현재 페이지에서 좌표 생성 성공까지 확인한 뒤 UI에 `현재 페이지의 텍스트와 위치를 분석할 수 있습니다.`만 표시한다. TextItemRecord의 text·bbox를 DOM, Console, 자동 결과 JSON에 기록하거나 UI 상태로 보관하지 않는다. 같은 페이지 배율 재렌더에서 다시 추출하지 않는 Unit 2.1 수명 계약도 유지한다.
- 검증: 형식, Node 70개, 실제 한글+이미지 PDF의 6 bbox, offset viewBox `[10,20,210,320]`·`UserUnit 2`·0/90/180/270도 합성 PDF의 50/100/200% 투영을 실제 `PDFPageProxy.getViewport()`와 대조했다. 원본 SHA-256, 빌드, Windows x64/ASAR 패키지, 개발·빌드·패키지 Electron 3경로, 실제 Windows 선택 창이 통과했다. 종료 반복은 개발 8/9·패키지 9/9이며 개발 즉시 종료 1회에서 OPEN-09가 재현됐다. 18회 모두 창 종료·종료 코드 0·포트 해제는 정상이다.
- 한계·후속: bbox는 글리프 윤곽·잉크·클리핑 영역을 보장하지 않는 근사 축 정렬 사각형이고 세로쓰기 증거는 합성 데이터뿐이다. sourceIndex별 실제 화면 대조는 다음 실행 순서인 Unit 2.5 Debug Overlay에서 수행한다. Text Layer, 줄/블록, 키워드, 해설·정답 영역, 지원 판정, Question·CBT, 저장, OCR/AI는 이번 범위가 아니다.

### ADR-027 — Unit 2.3 문맥 기반 제목 키워드 후보

- 상태: **채택 — Unit 2.3 구현·검증 완료**, 2026-09-02. 앱과 Windows x64/ASAR 패키지는 버전 0.2.3이다.
- 순서 예외: ROADMAP은 bbox 시각 대조를 위해 Unit 2.5를 2.3보다 먼저 두었지만, 사용자가 Unit 2.3을 명시적으로 요청했다. 요청 범위만 구현했으며 Unit 2.5를 완료·생략한 것으로 처리하지 않는다. 당시 다음 순서는 2.5로 기록했으며, 이후 사용자가 Unit 2.4도 명시적으로 요청한 두 번째 예외와 현재 순서는 ADR-028이 갱신한다.
- 입력·실패 계약: 순수 `findPageKeywordCandidates()`는 동일 documentRevision·pageNumber의 PageTextSource v1과 PageTextAssessment v1만 받는다. `text-usable`에서만 검색하고 `text-insufficient/unknown`은 `TEXT_NOT_USABLE`과 기존 reason code로 보류한다. 잘못된 source나 서로 맞지 않는 assessment에는 원문 없는 공개 실패 코드를 반환한다.
- 키워드·줄 계약: 고정 목록은 `해설/풀이/정답/답/Answer/Solution/Explanation` 일곱 개다. 영문은 대소문자를 구분하지 않고 더 긴 키워드를 먼저 검사한다. source item 순서와 `hasEOL`만으로 논리 줄을 만들고 같은 줄의 문자열은 새 공백이나 문자를 넣지 않고 연결한다. 따라서 분리된 `정`+`답`은 찾되 시각적 줄·문단·읽기 순서를 추정하지 않는다.
- 문맥·오탐 정책: 제한된 공백·글머리표 뒤 줄 시작에서 단독 제목, 구분 기호, 해설 본문, 허용 답 표기(①~⑩, 1~10, A~G)를 구분한다. `정답을 고르시오`, `답변`, `해설서`, `풀이과정`, 본문 중간 `Answer`, `Answer choices`, `Solution manual`, `Explanation guide` 고정 사례는 제외한다. 이는 측정된 정확도나 모든 출판물의 오탐 제거를 보장하지 않는다.
- 결과·개인정보: `PageKeywordCandidates v1`은 contract/source version, revision, pageNumber, count와 후보 근거만 가진다. 후보는 canonical/matched keyword, 종류·언어·문맥, 단일/분절 matchMode, sourceIndexes, 논리 줄 번호만 포함한다. 전체 주변 문장·bbox·region·questionId·정답 값·경로·PDF.js 객체는 포함하지 않는다. UI는 후보 원문 없이 개수·없음·보류만 표시하고 결과를 장기 보관하지 않는다.
- 검증: 형식, Node 81개, 실제 PDF.js 합성 fixture의 본문 `Answer`와 `Answer choices` 제외 및 `Explanation:` 후보 1개, 원본 SHA-256, 빌드, Windows x64/ASAR 패키지, 개발·빌드·패키지 Electron 3경로, 실제 Windows 선택 창이 통과했다. 종료 반복은 개발 7/9·패키지 9/9이며 개발 즉시 종료 두 번에서 기존 OPEN-09가 재현됐다. 18회 모두 창 종료·종료 코드 0·포트 해제는 정상이다.
- 제외 범위: 시각 bbox Debug Overlay, 좌표 기반 줄/블록 복원, 해설·정답 시작/끝 영역, 후보 점수·지원 판정, Question·정답 추출·마스크·CBT, 저장, OCR/AI는 Unit 2.3에 포함하지 않는다. 후보가 하나 이상이어도 CBT 지원이나 안전한 가림을 뜻하지 않는다.

### ADR-028 — Unit 2.4 해설·정답 영역 후보

- 상태: **채택 — Unit 2.4 구현·검증 완료**, 2026-09-02. 앱과 Windows x64/ASAR 패키지는 버전 0.2.4다.
- 순서 예외: ROADMAP은 bbox 시각 대조를 위해 Unit 2.5를 2.4보다 먼저 두었지만 사용자가 Unit 2.4를 명시적으로 요청했다. 후보 추론만 구현했고 Unit 2.5를 완료·생략한 것으로 처리하지 않는다. 다음 구현 순서는 2.5이며, 그 뒤 2.6 지원 판정이 필요하다.
- 입력·결과 계약: 순수 `inferPageAnswerRegions()`는 같은 revision·pageNumber와 페이지 geometry를 가진 PageTextSource v1, `text-usable` PageTextAssessment v1, PageTextCoordinates v1, PageKeywordCandidates v1만 받는다. 불충분·확인 불가 텍스트는 기존 reason code와 함께 건너뛰고 계약 불일치는 부분 결과 없이 공개 실패 코드로 끝낸다. `PageAnswerRegions v1`은 세션의 현재 페이지 후보 데이터이며 Mask 승인이나 지원 판정이 아니다.
- 줄·좌표 계약: source item 순서와 `hasEOL`로만 논리 줄을 만들고 각 줄의 TextItemRecord를 회전 전 PDF user space에서 합친다. source 순서의 Y 진행이 역전되거나 같은 높이에 큰 수평 간격이 있어 다단 가능성이 있으면 영역을 만들지 않는다. 고유 회전과 세로쓰기도 Unit 2.5 시각 검증 전까지 보류한다.
- 경계·순서 계약: 제목 줄에서 시작하고 다음 제목 바로 앞에서 끝낸다. `solution-then-answer`와 `answer-then-solution`을 별도로 반환하며 첫 제목 전 문제·보기 줄은 영역에 포함하지 않는다. 같은 종류 제목이 여러 개면 다문제 가능성으로 보류한다. 한 종류만 있으면 후보는 유지하되 다른 제목 누락을 기록한다.
- 누락 방지 한계: 다음 제목이 없는 마지막 영역은 Text Content 끝을 임시 경계로 사용하면서 `OPEN_ENDED_LAST_REGION`을 유지한다. 모든 영역은 `text-bounds-only`와 `NON_TEXT_CONTENT_UNVERIFIED`를 가지므로 이미지·수식·클리핑을 포함한 완전한 가림으로 승인할 수 없다. 단독 제목 뒤 본문이 없으면 별도 사유를 남긴다.
- 개인정보·UI: 결과에는 계약 버전, revision, pageNumber, 순서, sourceIndexes·논리 줄 경계, PDF user space rects와 reason code만 둔다. 전체 주변 원문·questionId·정답 값·Mask는 넣지 않는다. 일반 UI는 후보 수·없음·보류와 안전한 가림 미확인 상태만 표시하며 원문·좌표를 DOM·Console·자동 결과에 노출하거나 장기 보관하지 않는다.
- 검증: 형식, Node 92개, 실제 PDF.js 합성 fixture의 `해설→정답` 두 영역·문제/보기 제외·텍스트 전용 및 열린 마지막 경계·원본 SHA-256을 확인했다. 개발·빌드·패키지 Electron 3경로와 실제 Windows 선택 창도 통과했다. 종료 반복은 개발 7/9·패키지 9/9이며 개발 즉시 종료 두 번에서 기존 OPEN-09가 재현됐다. 18회 모두 창 종료·종료 코드 0·포트 해제는 정상이다.
- 제외 범위: Debug Overlay, 실제 화면 bbox 대조, 고정 지원 프로파일과 정확도 측정, 이미지·수식 영역, Question 소유 관계, 정답 값 추출, Mask·공개·채점·CBT, 저장, OCR/AI는 Unit 2.4에 포함하지 않는다.

### ADR-029 — Unit 2.5 명시적 개발자용 Debug Overlay

- 상태: **채택 — Unit 2.5 구현·검증 완료**, 2026-09-02. 앱과 Windows x64/ASAR 패키지는 버전 0.2.5다.
- 활성화 경계: `--debug-overlay`는 main 프로세스가 읽는 명시적 개발 진단 옵션이다. 이 옵션이 있을 때만 내부 renderer URL에 `debugOverlay=1`을 붙인다. 일반 `npm run dev`, 빌드 자산 실행과 패키지 직접 실행은 URL·panel·overlay DOM이 기존과 같고 진단 데이터를 보관하지 않는다.
- 입력·결과 계약: 순수 `createPdfDebugOverlayModel()`은 같은 revision·pageNumber의 PageTextCoordinates v1과 선택적인 PageKeywordCandidates v1/PageAnswerRegions v1만 받는다. 계약 불일치·잘못된 geometry는 부분 사각형 없이 공개 실패 코드로 끝낸다. 결과는 `viewport-css-px` 좌표, sourceIndex·candidate/region index, 종류·개수·공개 reason code만 가지며 PDF 원문·정답 값·경로·PDF.js 객체를 복사하지 않는다.
- 좌표·레이어 계약: 기존 PDF user space 근거를 PDF.js와 같은 viewport로 투영하고 실제 Canvas CSS width/height의 정수 반올림 차이를 보정한다. Canvas device pixel ratio와 backing bitmap은 사용하지 않는다. Text Item, 제목 키워드 근거, 영역 text rect와 전체 경계를 서로 다른 선과 `T/K/R` index로 같은 page surface에 그린다.
- 수명·재투영: 확대·축소, 높이 맞춤, 창 크기와 고유 회전 변화 때 현재 세션 근거를 새 Canvas CSS 크기에 다시 투영한다. 페이지·파일 변경, 분석 불가, dispose에는 기존 Overlay와 근거를 지운다. 숨김 버튼은 좌표 표시만 바꾸며 후보를 승인하거나 저장하지 않는다.
- 개인정보·안전: panel은 페이지·배율·회전·개수·분석 outcome만 표시한다. 진단 모드에도 PDF 원문 문자열은 DOM에 복사하지 않는다. 다만 답 위치를 시각적으로 드러내므로 일반 사용자/CBT 경로에서는 비활성 상태를 유지한다. Overlay는 pointer event를 받지 않고 Mask·원문 공개·채점 상태에 연결하지 않는다.
- 검증: 형식, Node 97개, 설치된 PDF.js 합성 fixture의 Text Item 7개·키워드 2개·영역 2개를 실제 Canvas 위에 대조했다. 100→125% 확대, 높이 맞춤과 창 크기 변경, 0/90/180/270도 고유 회전에서 Canvas와 Overlay CSS 크기·사각형 재투영을 확인했다. 일반 실행 DOM 비생성, 진단 DOM 원문 비복사, 숨김/표시, 개발·빌드·패키지 Electron 4/4와 실제 Windows 선택 창 1/1이 통과했다. 종료 반복은 개발 8/9·패키지 9/9이며 개발 즉시 종료 한 번에서 기존 OPEN-09가 재현됐다. 18회 모두 창 종료·종료 코드 0·포트 해제는 정상이다.
- 제외 범위: 새로운 키워드·영역 규칙, 실제 출판물 지원률·누락/침범 측정, 글리프 잉크·클리핑·이미지·수식 경계, 지원 판정, Question·정답 추출·Mask·공개·채점·CBT, 저장, OCR/AI는 Unit 2.5에 포함하지 않는다. 다음 구현 순서는 Unit 2.6이다.

### ADR-030 — Unit 2.6 분석 프로파일 일치와 CBT 착수 가능성 분리

- 상태: **채택 — Unit 2.6 구현·검증 완료**, 2026-09-02. 앱과 Windows x64/ASAR 패키지는 버전 0.2.6이다.
- 판정 경계: `PageSupportProfile v1`은 같은 revision·pageNumber의 PageTextAssessment v1과 usable 페이지의 PageKeywordCandidates v1·PageAnswerRegions v1만 받는다. 기존 근거를 재해석해 제목·영역을 새로 만들지 않으며 계약 불일치는 원문 없는 공개 오류로 끝낸다.
- 첫 분석 프로파일: `single-page-single-column-two-headings-v1`은 usable 텍스트, 정확히 한 해설 제목과 한 정답 제목, 정확히 두 영역, A/B 제목 순서, 첫 제목 앞 문제 내용과 각 영역 본문 근거를 요구한다. 모두 맞으면 `profile-match`, 명백한 제목 부족은 `not-supported`, 텍스트·읽기 순서·레이아웃 근거가 불확실하면 `hold`다.
- 안전 결정: `profile-match`와 `canStartCbt`를 분리한다. 현재 영역은 텍스트 bbox뿐이고 마지막 영역의 닫힌 끝, 이미지·수식, Question 소유 관계와 안전한 Mask를 입증하지 못했다. 따라서 모든 일치 결과에 `NON_TEXT_CONTENT_UNVERIFIED`, `OPEN_ENDED_LAST_REGION`, `SAFE_MASK_NOT_VERIFIED`, `QUESTION_OWNERSHIP_NOT_ESTABLISHED`를 유지하고 `canStartCbt: false`로 고정한다.
- 개인정보·UI: 결과와 일반 UI에는 프로파일 ID, 판정, 공개 reason code, 품질·후보/영역 개수·순서·종류 요약만 둔다. PDF 원문·좌표·정답 값·파일 경로·PDF.js 객체·Question은 복사하거나 장기 보관하지 않는다. 프로파일 일치 화면도 Mask·답 확인·채점을 활성화하지 않는다.
- 고정 행렬: A/B 후보 2개는 2/2 일치했고 보호 대상 Text Item 누락 0/6, 문제 Text Item 침범 0/3이었다. 미지원·보류 6개의 오일치는 0/6이었다. 전체 분포는 profile-match 2/8, not-supported 2/8, hold 4/8(50%), CBT 착수 가능 0/8이다. 두 A/B PDF.js 합성 fixture도 순서와 원본 SHA-256 불변을 확인했다.
- 실제 호환성 보완: 사용자 제공 Notion/Chromium PDF 한 건은 Text Item 111개와 이미지 paint 0개인데 참조 font style 네 개의 ascent/descent가 `NaN`, vertical이 생략돼 기존 어댑터에서 `INVALID_TEXT_SOURCE`가 됐다. 선택적인 font 보조값만 정규화해 비공백 186자·판독 비율 1의 `text-usable` 근거를 보존했다. PDF.js source 순서에서 footer `제목 없음1`이 `정답 ④` 뒤에 붙는 현상은 오탐 방지를 위해 추정 복구하지 않아 정답 제목 누락·미지원으로 유지한다.
- 검증: 형식, Node 103개, 빌드 22 modules, Windows x64/ASAR 패키지, 개발자 진단·일반 개발·빌드·패키지 Electron 4/4와 실제 Windows 선택 창 1/1이 통과했다. 종료 반복은 개발 7/9·패키지 9/9이며 개발 즉시 종료 두 번에서 기존 OPEN-09가 재현됐다. 18회 모두 창 종료·종료 코드 0·포트 해제는 정상이다.
- 제한·인계: 고정 행렬은 합성 Text Item과 작은 실제 PDF.js 합성 fixture에 한정된다. 실제 Notion/Chromium 출력 한 건은 font metadata 호환성과 footer source 순서만 확인한 진단 샘플이며 지원률·안전한 가림 근거가 아니다. 실제 출판물 대표 행렬, 글리프·클리핑·이미지·수식, 픽셀 누출/과다 가림은 검증하지 않았다. Unit 3.0 구조 검토는 가능하지만 Phase 3.1 기능 전에 지원 범위 축소·대표 샘플 확보·Phase 4.1 수동 보정 선행 중 안전한 경로를 결정해야 한다. Mask·Question·정답 추출·공개·채점·CBT·저장·OCR/AI는 Unit 2.6 범위 밖이다.

## 6. 확인한 자료와 해석의 한계

기술 근거 링크는 각 주장 가까이에 기재했다. PDF.js 공식 API·소스·예제와 Electron 공식 문서를 확인했으며, Unit 0.2에서 Node.js LTS·Vite 요구사항과 실제 npm 패키지의 engines/exports를 다시 확인했다.

위 자료는 사용할 API와 프로세스 경계를 뒷받침한다. **규칙 기반 CBT 인식률, 우리 마스크의 안전성, 특정 PDF 호환성, 성능은 이 프로젝트에서 아직 시험하지 않았다.** 이 문서의 인식 방법·MVP 제한·실패 정책은 공식 라이브러리가 보장한 기능이 아니라 프로젝트 설계 제안이다.
