- 작성일: 2026-08-31
- 문서 버전: `0.1.2`
- 갱신일: 2026-09-01
- 상태: Unit 1.2 파일 드롭 구현·기능 검사 통과. 기존 종료 GPU 오류로 전체 완료 보류. Unit 1.0과 1.3 이후 기능은 미착수.

## 1. 요구사항 분석

제품은 PDF 편집기가 아니라 PDF 화면에 학습 상태를 덧붙이는 로컬 CBT다. 가장 큰 위험은 파일을 표시하는 일이 아니라, 공개 전 정답을 놓치지 않고 가리면서 문제·보기를 보존하고 올바른 정답을 해당 문제와 연결하는 일이다.

| 요구사항 | 현재 해석·반영 위치 |
| --- | --- |
| Electron·Vite·Vanilla JS·npm·PDF.js | 기술 선택은 사용자 요구로 확정. 버전과 패키징 방식은 Unit 0.2에서 결정 |
| 로컬 사용·외부 자동 전송 금지 | 앱 자산 로컬 번들, 권한/네트워크 제한, 오프라인 패키지 검증 |
| PDF 원본 불변 | 읽기 전용 입력, 별도 화면 레이어, 사용 전후 해시 검증 |
| 파일 선택·드롭·페이지·배율 | Phase 1에서 순서대로 구현 |
| 텍스트·좌표·키워드·영역 | Phase 2. 추출과 의미 추정을 분리 |
| 가림·선택·공개·채점 | Phase 3. 채점 불가를 정상 결과 중 하나로 정의 |
| 다양한 PDF 형식과 A~G 사례 | 아래 사례별 지원 경계 및 Phase 4/9 확장 |
| 자동 실패 시 수동 보정·규칙 재사용 | 보정 Phase 4, 영구 규칙 저장 Phase 5 |
| 향후 문제·학습·통계·OCR·AI | 데이터 경계만 준비. 세부 Unit은 Phase 4~10 |
| 문서 5개·18개 Bible 항목·Unit 완료 10항목 | 해당 문서와 CHANGELOG에 반영 |
| 최초 요청의 문서 작성 후 중단 | Unit 0.1에서 준수. 이후 각 Unit의 명시적 요청에 따라 0.4의 환경 검증까지만 수행 |

## 2. 빠진 내용과 요구사항 사이의 긴장

아래는 사용자 요구를 임의로 확정한 것이 아니라 **검토 가능한 기본 제안**이다. 문서 승인을 받기 전에는 구현하지 않는다.

| 쟁점 | 충돌·누락 내용 | 제안 및 결정 시점 |
| --- | --- | --- |
| 범용 PDF와 MVP 범위 | 자동 문제 분리는 Phase 4인데 임의 PDF로 CBT를 보장하려면 분리가 선행되어야 함 | 첫 MVP를 검증된 단순 프로파일로 제한. 동의하지 않으면 Phase 4 일부를 앞당겨 범위 재설계 |
| 해설 위치와 정답 추출 | 가릴 영역을 찾았다고 정답 번호를 안다는 뜻은 아님 | 두 결과를 독립 관리. 영역은 확실하고 답만 불명이면 공개는 허용하고 채점은 보류 |
| 정답 없음·복수 정답 | 미추출·충돌·복수 선택형의 처리 미정 | 4/5지 단일 정답만. 애매하면 `채점 불가`, 임의 채점 금지 |
| 보기 수 | 4지·5지가 예시로만 존재 | 사용자가 페이지별 4/5지 선택. 공개 후 잠금; 자동 보기 수 검출은 문제 분리 단계에서 재검토 |
| 페이지 이동과 문제 이동 | 한 페이지가 한 문제라는 전제가 성립하지 않음 | MVP UI는 페이지 이동. questionId는 독립적으로 설계 |
| 답 확인 전 화면 | 분석 시간이 걸리는 동안 원문이 먼저 나타날 수 있음 | CBT 모드 전체 페이지 덮개 → 분석·마스크 준비 완료 후 표시 |
| 자동 분석 실패 | 수동 보정이 MVP 밖이므로 대체 경로가 없음 | 실패 이유를 안내하고 기본은 가림 유지. 사용자가 `원문 보기` 또는 다른 페이지/파일 선택 |
| 가림과 Text Layer | 불투명 덮개 아래 텍스트가 선택·복사·접근성 트리에 남을 수 있음 | 가린 span 또는 공개 전 페이지 Text Layer 비활성화. 보안 기능은 아니며 접근성 한계 기록 |
| 상태 보존 | 앱 종료·페이지 재방문·재시도 정책 미정 | 페이지 재방문은 유지, PDF 닫기/교체·종료는 초기화. 영구 기록과 재시도는 Phase 5 |
| 실행 OS·배포 | OS/CPU·설치형/포터블·코드 서명 요구 미정 | Windows x64 우선 제안. 최소 OS와 로컬 패키지 도구는 0.2, 패키지 실행은 0.4 |
| 암호·손상·특수 PDF | 비밀번호·XFA·첨부·링크·스크립트 처리 미정 | 암호가 필요하면 MVP 미지원 안내. 동적 양식/실행 기능은 지원하지 않고 정적 페이지 중심 |
| 파일 크기·성능 | 최대 페이지·메모리·로딩 시간 요구 없음 | 1.6에서 기준 환경과 측정 결과를 기록한 뒤 제한 설정. 숫자를 현재 보장하지 않음 |
| Local First와 개발 설치 | npm 다운로드까지 인터넷을 전혀 쓰지 않는지 불명확 | 개발 준비는 다운로드 허용 가능, 배포된 기본 기능은 오프라인 필수로 구분 |
| 검증 입력 | 실제 PDF, 기대 마스크·정답 데이터가 없음 | 1.0에서 합성 샘플 준비. 실제 대표 PDF 확보 후 지원 범위를 확인; 지금 정확도 약속 없음 |

문서 검토의 주요 판단은 **① 제한된 첫 MVP 범위, ② Windows 우선, ③ 세션 메모리만 유지, ④ 암호 PDF 유보, ⑤ 불확실할 때 원문을 자동 공개하지 않음**이다. 이 기본안을 바꿀 수 있으며 선택지나 샘플이 없다는 이유로 이번 문서 작성은 중단하지 않았다.

## 3. 기술적 타당성과 검증 우선순위

아래 난이도는 설계 추정이다. 일정 견적이나 실측 성능이 아니다.

### 3.1 Text Layer 기반 해설/정답 위치 탐지는 가능한가?

**제한된 형식에서는 가능성이 높다. 범용 인식 정확도는 아직 검증되지 않았다.** 실제 분석 입력은 Text Layer DOM이 아니라 `getTextContent()` 결과다. PDF.js는 페이지의 텍스트 내용과 viewport를 제공한다. [PDFPageProxy 공식 API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-PDFPageProxy.html).

우리 설계 판단: 해당 출력에는 문제·보기·해설이라는 의미가 보장되지 않는다. 글자가 여러 항목으로 나뉘고 시각적 읽기 순서와 항목 순서가 다르거나, 수식·그림·윤곽선 글자가 의미 있는 텍스트로 나오지 않을 수 있으므로 줄/블록 복원과 문맥 검사가 필요하다. `정답 ③`을 읽는 난이도보다 “그 ③이 어느 문제의 답인가”와 “해설은 어디서 끝나는가”의 난이도가 높다.

우선 검증: 한글 분절과 짧은 `답`의 오탐, 정답·해설 순서, bbox 정확도, 해설에 포함된 그림·수식. **난이도: 텍스트 추출 중간, 영역 의미 추정 높음.** Unit 2.1~2.6에서 확인한다.

### 3.2 다양한 레이아웃을 어느 수준까지 규칙으로 처리할 수 있는가?

단일 열·명확한 제목·일관된 순서·동일 페이지 안의 완결 구조가 출발점이다. 키워드 사전, 줄 간격, 제목 경계, 열/블록 관계를 함께 쓰면 일부 출판 형식을 지원할 수 있다는 설계 가설이다. “모든 출판사에 공통인 정규식 하나”로 해결할 계획은 채택하지 않는다.

| 사례 | 첫 MVP 제안 | 장기 구조와 검증 |
| --- | --- | --- |
| A: 문제 → 보기 → 해설 → 정답 | 지원 프로파일 검증 대상 | 해설·정답의 별도 영역을 같은 questionId에 연결 |
| B: 문제 → 보기 → 정답 → 해설 | 지원 프로파일 검증 대상 | A와 순서를 바꿔도 영역 추정·공개·채점 일치 |
| C: 한 페이지 여러 문제 | CBT 미지원 안내 | Phase 4.2 여러 Question와 독립 Region |
| D: 문제의 다음 페이지 연속 | CBT 미지원 안내 | Phase 4.3 여러 pageRefs, 문제 연결 후보와 보정 |
| E: 해설이 다음 페이지에 존재 | CBT 미지원 안내 | Phase 4.3 문항-해설 명시적 연결; 다음 페이지를 무조건 연결하지 않음 |
| F: 텍스트 없는 스캔 | 원문 열람만, 분석 불충분 안내 | Phase 9 선택적 로컬 OCR과 좌표 역변환 |
| G: 출판사마다 다른 명칭 | 기본 키워드로 시작, 일치하지 않으면 보류 | 버전 있는 프로파일·수동 보정·Phase 5 규칙 저장 |

다단·반복 지문·분리된 정답표·복수 정답·키워드가 없는 해설까지 범위를 넓히면 잘못된 연결 위험이 급증한다. 프로파일은 고정 절대 Y값이 아니라 허용된 패턴과 관계, 실패 조건으로 정의한다. 새 파일이 기존 샘플과 비슷하다는 이유만으로 안전하다고 단정하지 않는다.

**잔여 위험:** 미지원 형식을 자동으로 완벽히 찾아내는 것도 어렵다. 모든 경고 없이 통과한 새 PDF의 누출 가능성을 0으로 보장하지 않는다. 지원 목록과 검증 한계를 사용자에게 알리고, 의심되는 조건에서 보수적으로 보류한다. 수동 보정이 실사용에 필수라는 결과가 나오면 MVP 범위를 재협의한다. **난이도: 높음.**

### 3.3 Canvas + Text Layer + Mask Layer가 적절한가?

**적절한 책임 분리다.** 원본 표시를 그대로 두면서 학습 상태에 따라 마스크만 변경할 수 있다. Text Layer는 추출 자체에 필수는 아니지만 향후 선택·접근성·검색에 활용할 여지가 있다.

추가로 필요한 것은 공통 viewport, 로딩/불확실 상태의 전체 덮개, 공개 대상의 questionId 소유권, 텍스트의 우회 노출 억제다. 화면 좌표를 단순 배율 곱셈만으로 처리하지 않는다. Canvas 내부 픽셀과 CSS 크기를 분리하고 렌더 취소·완료 순서를 맞춰야 한다. PDF.js 예제도 비동기 렌더와 Canvas 동시 사용 제한을 설명한다. [공식 렌더링 예제](https://mozilla.github.io/pdf.js/examples/).

**난이도: 중간~높음.** 좌표 Unit 2.2, 마스크 Unit 3.1, 프레임·상태 통합 Unit 3.7이 검증 관문이다. Blur보다는 불투명 Overlay를 먼저 택한다.

### 3.4 한 페이지 여러 문제에는 어떤 구조가 필요한가?

**페이지와 문제를 분리해야 한다.** PDF 페이지는 렌더링 단위이고 Question은 학습 단위다. Question 하나가 여러 페이지와 여러 해설/정답 영역을 가질 수 있고, 페이지 하나에 여러 Question이 놓일 수 있다.

제안 관계: `Document → Pages`, `Document → Questions`, `Question → pageRefs[] + regionIds[]`, `Region → page + rects[]`, `Attempt → questionId`. 첫 MVP에서는 pageRefs 길이 1과 임시 page-single 모드만 사용한다. 문제 번호 문자열도 문서 안에서 중복될 수 있으므로 영구 ID로 쓰지 않는다.

여러 질문이 공유하는 지문, 공통 해설, 애매한 경계는 단순한 다음 문제 번호 탐지만으로 풀리지 않는다. Phase 4.0에서 공유 영역과 공개 정책을 재검토한다. 현재 복잡한 그래프 DB나 전체 도메인 프레임워크를 만들 필요는 없다. **난이도: 구조 중간, 자동 분리 높음.**

### 3.5 스캔 PDF와 일반 PDF는 어떻게 구분할 것인가?

**페이지별 분석 가능성을 판정한다. 스캔 여부의 완벽한 이진 판정은 목표가 아니다.** 텍스트가 비었다고 스캔으로 확정하지 않고, 텍스트가 있다고 쓸 만한 페이지로 확정하지 않는다. OCR이 이미 포함된 스캔, 페이지 번호만 있는 이미지 페이지, 손상된 문자 매핑, 텍스트와 이미지가 섞인 문서를 고려한다.

1차 신호는 유효 문자열·문자량·문자 품질·좌표 범위다. 필요하면 이미지 연산과 면적을 보조 신호로 평가할 수 있으나 “이미지가 있으므로 스캔” 같은 규칙은 쓰지 않는다. `getOperatorList()`는 분석 자료를 제공할 뿐 의미 분류의 답을 제공하지 않는다. [PDFPageProxy 연산 목록 API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-PDFPageProxy.html).

결과는 usable/insufficient/unknown으로 표현하고 후자의 경우 자동 분석을 보류한다. 임계값·이미지 조사 채택 여부는 샘플을 본 뒤 결정한다. **난이도: 보수적 분류 중간, 높은 신뢰도의 분류 높음.**

| 3 | 해설 끝 경계를 놓치거나 문제를 가림 | 2.4 / 2.6: 사람 기준 영역과 비교 | 규칙 수정·지원 범위 축소·수동 보정 일정 검토 |
| 4 | 문제/정답 연결이 틀림 | 2.6 / 3.5: 단일 답 근거 대조 | 보류. 잘못된 자동 채점 금지 |
| 5 | 첫 프레임/배율 변경에서 답이 노출됨 | 3.1 / 3.7: 느린 분석·빠른 이동 포함 실제 화면 | 전체 덮개와 준비 상태 원자적 전환 수정 |
| 6 | 장문·이미지 PDF에서 앱이 멈춤 | 1.6 / 3.7: 메모리·취소·연속 열기 | 자원 제한·캐시·해제 정책 보강 |

성공 사례만으로 검증하지 않는다. ROADMAP의 실패/미지원 샘플도 같은 비중으로 확인한다. 첫 MVP의 유용성은 지원 샘플에서 실제 풀이가 끝나는지로, 안전성은 누출·침범·오채점과 미지원 오승인으로 각각 평가한다.

## 4. 기술 결정 기록

상태의 의미: `사용자 지정`은 요구사항에서 선택된 방향이다. `제안·승인 대기`는 이번 검토의 추천안이다. `결정 유보`는 해당 Unit에서 증거를 수집한 뒤 확정한다. 승인 이후 변경 시 기존 기록을 지우지 않고 대체 결정과 이유를 덧붙인다.

### ADR-001 — Electron과 Vanilla JS

- 상태: **사용자 지정**.
- 결정: Electron + Vite + Vanilla JavaScript + HTML/CSS + npm을 사용한다.
- 이유: 로컬 파일을 다루는 데스크톱 앱과 사용자가 정한 단순한 프론트엔드 구성을 따른다.
- 대안/대가: React/Vue는 현재 도입하지 않는다. UI 상태·모듈 경계를 직접 관리해야 하며 Electron의 배포 크기·메모리·업데이트 책임이 생긴다.
- 재검토: UI 복잡성 때문에 현재 구조로 유지보수가 어려워질 때만 근거를 갖고 제안한다.

### ADR-002 — PDF.js를 표시·추출 어댑터로 사용

- 상태: **사용자 지정**; 어댑터 경계는 **제안·승인 대기**.
- 결정: PDF.js의 표시·텍스트·좌표를 쓰고, 문제 의미 분석은 별도 모듈에 둔다. 전체 generic viewer를 무조건 복제하지 않는다.
- 이유: 필요한 데이터에 접근하면서 CBT UI와 수명 관리를 직접 제어하기 위함이다.
- 대가: 글꼴·자산·메모리·취소·좌표 정렬을 직접 검증해야 한다. PDF.js API 문서의 draft/master 내용이 선택한 안정판과 같다고 가정하지 않는다.
- 재검토: 버전 업그레이드 시 본체·worker·자산을 함께 검증한다.

### ADR-003 — 첫 MVP의 단순 형식 지원

- 상태: **제안·승인 대기**.
- 결정: 같은 페이지의 단일 문제·단일 열·4/5지 단일 정답과 검증된 A/B 형식에 한정한다.
- 이유: 자동 분리·페이지 연결을 MVP 이후로 남긴 사용자 계획을 지키면서 검증 가능한 첫 결과를 만들기 위함이다.
- 대안/대가: 임의 PDF를 바로 풀 수는 없다. 범용 지원을 요구하면 수동 보정·문제 연결을 먼저 넣도록 일정 변경이 필요하다.
- 재검토: Unit 2.6 샘플 결과와 사용자 문서 구성에 따라 조정한다.

### ADR-004 — OCR을 MVP에서 제외

- 상태: MVP OCR 유보는 **사용자 허용 범위에서 채택한 제안·승인 대기**.
- 결정: 원래의 텍스트 데이터를 우선 분석한다. OCR은 Phase 9에서 로컬 실행부터 검토한다.
- 이유: 텍스트·좌표 정확도 문제와 OCR 오인식 문제를 한꺼번에 떠안지 않기 위함이다.
- 대가: 스캔/텍스트 불량 페이지는 CBT 불가. 원문 열람과 이유 안내는 유지한다.
- 재검토: 핵심 사용자 PDF가 대부분 스캔이라면 MVP 제품 범위부터 재검토한다.

### ADR-005 — 별도 불투명 Overlay와 안전한 보류

- 상태: 원본 불변·별도 레이어는 **사용자 지정**; 불투명 기본값과 전체 덮개는 **제안·승인 대기**.
- 결정: 개별 Region 마스크를 questionId에 연결한다. 준비 전/분석 불확실 시 전체 페이지를 가린다. 원문 노출은 별도의 사용자 선택이다.
- 이유: 한 가지 마스크 상태로 로딩 실패와 정답 공개를 혼동하지 않고 원본을 보존하기 위함이다.
- 대가: 미지원 페이지에서는 문제까지 덮이므로 편의성이 떨어진다. 자동 인식의 실수 자체를 없애는 보안 장치가 아니다.
- 재검토: 수동 보정·다문제·접근성 확장 시 공개 경계를 다시 검토한다.

### ADR-006 — 좌표는 PDF 공간, 레이어는 viewport 공유

- 상태: **제안·승인 대기**.
- 결정: 화면 배율과 무관한 PDF user space의 영역을 저장하고 표시할 때 투영한다.
- 이유: 확대·DPI·회전·창 크기에 따라 저장 좌표가 변하지 않게 하기 위함이다.
- 대가: bbox는 근사치이며 변환·글꼴·잘림 경계를 검증해야 한다. 단순 CSS 비율만 적용하는 방식은 채택하지 않는다.
- 재검토: Unit 2.2에서 API와 좌표 시험을 확정하고 Phase 4 수동 지정·Phase 9 OCR 좌표를 연결할 때 재검토한다.

### ADR-007 — 메모리 데이터와 조건부 채점

- 상태: **제안·승인 대기**.
- 결정: 현재 열린 PDF의 상태만 메모리에 유지한다. 영구 DB는 만들지 않는다. known 단일 정답만 채점한다.
- 이유: 학습 기록을 Phase 5로 분리하고 분석 실패가 오답 데이터로 누적되는 것을 막기 위함이다.
- 대가: 종료 후 복원되지 않으며 재시도 이력도 없다. UI에서 저장 범위를 설명해야 한다.
- 재검토: Phase 5.0에서 문서 해시·영구 식별자·변경 감지·마이그레이션과 함께 설계한다.

### ADR-008 — 격리된 Electron 경계와 오프라인 패키지

- 상태: Local First는 **사용자 지정**; 보안 경계·패키지 검증 방식은 **제안·승인 대기**.
- 결정: 파일 접근은 main, 좁은 연결은 preload, PDF 표시·학습 UI는 격리된 renderer에 둔다. 외부 의존 없는 로컬 테스트 패키지를 만든다.
- 이유: 로컬 PDF도 안전한 입력이라고 전제할 수 없고, 개발 서버 성공만으로 실제 설치 앱 동작을 검증할 수 없기 때문이다.
- 대가: 파일 드롭·IPC·CSP·자산 프로토콜에 대한 통합 시험이 필요하다. 드롭은 폐기된 File.path 가정 대신 선택 버전의 지원 API를 사용한다. [Electron webUtils](https://www.electronjs.org/docs/latest/api/web-utils).
- 재검토: 0.2~0.4에서 main/preload 모듈 형식·허용 API·프로토콜·패키징 도구 확정. 서명과 공개 배포는 후속 검토다.

### ADR-009 — 검증을 독립 Unit으로 관리

- 상태: **제안·승인 대기**.
- 결정: 1.6, 2.6, 3.7 검증 관문과 2.5 선행 실행을 추가한다.
- 이유: 렌더링, 좌표, 인식, 공개 타이밍은 각기 다른 실패 원인이기 때문이다.
- 대가: 눈에 보이는 기능 증가가 없는 작업이 포함되지만 추후 오류 원인 추적이 쉬워진다.
- 재검토: Unit이 지나치게 커지면 번호를 보존하며 하위 작업을 분리한다. 테스트하지 않은 항목을 완료로 바꾸지 않는다.

### ADR-010 — AI는 기본 CBT와 분리

- 상태: **사용자 지정**.
- 결정: AI 요약·암기 포인트·유사 문제는 Phase 10의 선택 기능이다. 지금 서비스 코드·API 키·SDK를 만들지 않는다.
- 이유: 인터넷·제공자·비용·개인정보 정책이 기본 학습 기능의 사용 조건이 되면 안 된다.
- 대가: 생성 품질, 전송 동의, 로컬 모델 가능성은 나중에 별도로 검증해야 한다.
- 재검토: 10.0에서 서비스 경계와 데이터 전송 범위를 먼저 승인받는다.

### ADR-011 — Unit 0.2 런타임·지원 대상·의존성 고정

- 상태: **채택 — 사용자의 Unit 0.2 착수 요청에 따른 구현 결정**, 2026-08-31.
- 결정: 프로젝트 지원/검증 대상은 Windows 11 x64. 개발 Node 24.19.0, npm 10.8.2를 검증 기준으로 삼고 Node 24.19 이상인 24 LTS만 허용한다. `.node-version`과 `.npmrc`/engines 및 실행 전 검사로 버전 실수를 안내한다.
- 고정 직접 의존성: Electron 44.0.0, Vite 8.2.2, `@electron/packager` 20.3.0, Prettier 3.9.6. npm 레지스트리 metadata와 설치된 package.json을 확인했으며 package-lock.json으로 전이 의존성을 고정했다.
- 이유: Unit 0.2 당시 시스템 Node 20.19.1은 지원 종료 상태여서 사용하지 않았다. 시스템 Node나 영구 PATH를 바꾸지 않고 별도 Node 24.19.0으로 개발·검증했다. 이후 확인한 환경은 ADR-015와 [README](../README.md)를 따른다. [Node.js 지원 상태](https://nodejs.org/en/about/previous-releases).
- 플랫폼 구분: Electron 자체는 Windows 10 이상을 안내하지만 프로젝트가 Windows 10까지 검증했다는 뜻은 아니다. 이번 최소 지원 대상은 실제 검증 환경인 Windows 11 x64다. [Electron 공식 플랫폼 안내](https://github.com/electron/electron#platform-support).
- 확인 결과: Windows build 26200 x64에서 기본 실행 통과. Electron 내부 런타임은 Node 24.18.1 / Chromium 152.0.7977.54로 개발용 Node와 별개다.
- 추가 발견: Electron 44는 npm 패키지 설치 후 바이너리를 지연 다운로드한다. `npm run setup:electron`으로 공식 설치 명령을 명시적으로 실행하도록 했다. 최초 바이너리 준비에는 인터넷이 필요하며 앱의 원격 서비스 의존성을 뜻하지 않는다.
- 재검토: 업데이트 시 lockfile과 실제 런타임 조합을 함께 확인한다. Windows 10/ARM64/macOS/Linux 지원을 자동으로 확대하지 않는다.

### ADR-012 — ESM main/renderer, CommonJS preload, 두 실행 경로

- 상태: **채택 — Unit 0.2 구현 및 기본 연결 확인**. ADR-001/002/008의 현재 필요한 경계를 구체화한다.
- 결정: main과 renderer는 ESM, sandbox preload는 `.cjs`를 사용한다. preload는 읽기 전용 `runtimeInfo`만 노출하며 IPC·파일 API는 아직 만들지 않는다. [Electron sandbox preload 제약](https://www.electronjs.org/docs/latest/tutorial/esm#sandboxed-preload-scripts-cant-use-esm-imports).
- 개발 경로: Node 실행 스크립트가 Vite 준비 완료 후 Electron을 실행한다. `127.0.0.1:5173`과 개발용 WebSocket만 허용하고 strictPort를 사용한다. main/preload 변경은 명시적 재시작이 필요하다.
- 빌드 경로: `local-cbt://app/index.html`로 dist의 HTML/JS/CSS만 제공한다. 사용자 파일 경로를 받지 않고 호스트·메서드·상대 경로·Windows 경로 문자를 검사한다. 자산 유형은 현재 필요한 것만 허용하며 PDF 관련 유형은 후속 Unit에서 추가한다. [Electron protocol API](https://www.electronjs.org/docs/latest/api/protocol#protocolhandlescheme-handler).
- 보안: Node 통합 비활성화, context isolation·sandbox·webSecurity 활성화, 권한·탐색·새 창 기본 거부. 개발 CSP의 inline style/루프백 WebSocket 예외는 빌드 CSP에 포함하지 않는다.
- 대가: 가벼운 확인 화면에도 수명/권한 경계가 필요하지만 이후 PDF 기능 때문에 격리 설정을 뒤집지 않아도 된다. 이를 Application Shell이나 파일 접근 구현으로 확대하지 않았다.
- 검증: Unit 0.2의 개발/빌드 자산 연결과 정상 경로 Console Error·pageerror 0을 확인했다. Unit 0.4의 패키지·경로 거부·CSP·권한 검증 결과는 ADR-015/016에 추가한다.
- 수정 근거: 실제 개발 명령 시험에서 GUI 프로세스의 `windowsHide: true`가 창을 숨기는 문제를 발견했다. Electron GUI만 `false`로 수정했고, 숨겨진 콘솔 helper와 사용자 앱 창의 역할을 구별했다. 수정 후 보이는 창 열기·닫기·서버 종료를 확인했다.

### ADR-013 — 공식 Packager와 최소 빌드 설정

- 상태: **채택 — Unit 0.2 설정 구현, Unit 0.4 실제 패키지 검증 완료**. 추가 결정은 ADR-015/016.
- 결정: Vite는 renderer만 빌드하고 Electron main/preload는 직접 실행한다. 공식 `@electron/packager`로 Windows x64 폴더/ASAR 패키지를 만들도록 명령을 준비했다. [Electron Packager](https://electron.github.io/packager/main/).
- 이유: 현재 main/preload 번들·자동 재시작·배포/서명 프레임워크까지 추가할 필요가 없다. Vite 전용 Electron 플러그인이나 Forge 전체 구성을 먼저 도입하지 않는다.
- 구현 세부: 설치된 20.3.0의 named export `packager`를 사용한다. electron/·dist/·package.json만 복사하며 개발 문서·스크립트·개인 파일·node_modules는 제외한다. 현재 런타임 npm 의존성이 없으므로 prune은 사용하지 않는다. 런타임 의존성을 추가하면 포함 규칙을 먼저 재검토한다.
- 출력: `release/local-pdf-cbt-win32-x64/`. 기존 출력은 자동 덮어쓰지 않는다. 설치 프로그램, 서명, 업데이트, 공개 배포는 수행하지 않는다.
- 한계: Unit 0.2 당시에는 Vite 빌드와 dist 실행만 확인했다. Unit 0.4에서 ASAR·독립 복사본·앱 네트워크 차단 조건을 검증했으며, 새 Windows/VM 전체 검증은 수행하지 않았다.
- 코드 형식: Prettier의 2칸·세미콜론·작은따옴표·LF를 적용한다. 기존 docs는 형식만 바꾸는 대규모 변경을 피하려고 자동 포맷 대상에서 제외한다.

### ADR-014 — Unit 0.3 기본 Shell과 읽기 전용 상태 표시

- 상태: **채택 — 사용자의 Unit 0.3 요청에 따른 구현·실제 화면 검증**, 2026-08-31. ADR-012의 연결 확인 화면만 확장하며 보안·파일 접근 경계는 유지한다.
- 구성: 한국어 정적 HTML의 앱 머리말, 빈 문서 작업 공간, 앱 상태 영역, 하단 안내. `src/main.js`는 초기화, `src/ui/runtime-status.js`는 전달받은 실행 정보의 표시만 담당한다. 기본 스타일과 Shell 배치는 CSS 파일로 나눈다.
- 상태: preload의 기존 읽기 전용 `runtimeInfo`로 연결 완료·Electron 버전을 표시한다. 정보가 없거나 버전 문자열이 비어 있으면 `Electron 실행 필요`와 실행 명령을 안내한다. `textContent`를 사용하며 색상과 문구를 함께 표시한다. `role="status"`·`aria-atomic`을 사용하고 장식 아이콘은 접근성 트리에서 제외한다.
- 배치: 기본 1120×760, 최소 640×480의 테두리 포함 논리 픽셀. 기본 화면의 빈 작업 공간과 상태를 함께 읽을 수 있도록 정했다. 콘텐츠 너비 56rem(기본 896 CSS px) 이하에서는 상태를 작업 공간 아래로 배치하고, 30rem 이하에서는 상태 항목도 한 열로 배치한다. 창이 작거나 확대된 상태에서는 잘라 숨기지 않고 문서 세로 스크롤을 허용한다. 창 크기·위치 저장은 추가하지 않는다.
- Local First: 시스템 글꼴·정적 인라인 SVG만 사용해 외부 글꼴/이미지·아이콘 패키지를 추가하지 않는다. 새 IPC, CSP 예외, 프로토콜 자산 유형도 필요하지 않다.
- 범위: 파일 선택/드롭·PDF 렌더링·페이지·배율 제어·학습 버튼을 만들지 않는다. 빈 화면이 드롭 영역이나 실행 가능한 CBT로 오해되지 않도록 미지원 상태를 명시한다. 새 상태 저장소·이벤트 버스·미래 서비스·의존성을 선행 구축하지 않는다.
- 검증: 개발/빌드 자산 모드의 실제 Electron 창에서 한국어 화면, 연결 정보, 4가지 창 크기와 최소 창의 200% 확대, 최소 크기 제한, 가로 넘침 없음·하단 스크롤 도달, 기존 격리 설정을 확인했다. 정보 없는 상태는 개발 모드의 표시 함수에 `undefined`를 전달해 확인했다. 확대는 검증 도구에서 적용했으며 앱 확대 기능 구현이 아니다.
- 제한/인계: Unit 0.3 정상 화면 경로의 renderer Console Error·pageerror·경고는 0이었다. 창 생성 직후 즉시 종료한 첫 시험에는 내부 GPU 진단 로그가 있었고, 당시 화면 표시 후 정상 종료에서는 재현되지 않았다. Unit 0.4의 후속 결과는 ADR-016/OPEN-09을 따른다. 스크린 리더·다중 모니터·Windows 디스플레이 배율별 실사용 검증은 수행하지 않았다.
- 재검토: 파일 열기는 Unit 1.1, 드롭은 1.2, 렌더링은 1.3, 학습 UI는 Phase 3에서 필요한 제어와 상태를 추가한다. 실제 PDF 레이어가 생기면 세로 스크롤의 소유 영역을 다시 정한다.

### ADR-015 — 반복 가능한 환경 검사와 로컬 패키지 검증 범위

- 상태: **채택 — Unit 0.4 주요 검사 통과, 종료 진단은 OPEN-09로 추적**, 2026-08-31 작성 / 2026-09-01 갱신.
- 도구: Node 내장 테스트 실행기로 자산 프로토콜·요청 허용 목록·CSP 16개를 검사한다. 실제 Electron의 개발/빌드/패키지 3경로는 개발 전용 playwright-core 1.62.1로 제어한다. 실제 Windows 닫기 동작은 PowerShell 종료 검사로 별도 반복한다. 별도 브라우저·제품 런타임 의존성은 추가하지 않는다. 도구 버전은 npm metadata와 설치 파일을 확인해 고정했다.
- 실행 기준: 이 Unit의 실제 환경은 Windows 11 x64 build 26200, 개발 Node 24.19.0(별도 런타임) 및 24.20.0(현재 시스템), npm 11.19.0이다. 기존 Node 최소값과 npm 10~11 허용 범위는 유지하고 packageManager만 이번 npm 기준으로 갱신했다. 시스템 Node/npm 설치나 영구 PATH는 변경하지 않았다.
- 패키지: Windows x64 폴더/ASAR을 실제 생성했다. 앱 ASAR 루트가 dist/·electron/·package.json만 포함하고 테스트·문서·node_modules가 없는지 확인했다. 한글·공백 경로의 새 프로젝트에서 npm ci·Electron 준비·테스트·패키징을 재현하고, 앱 폴더만 복사한 독립 실행도 확인했다. 실행 파일 하나가 아니라 Electron 자산·DLL·라이선스를 포함한 폴더 전체를 사용한다.
- 오프라인 조건: 새 테스트 프로필의 패키지를 연결 불가능한 루프백 프록시와 우회 금지 조건으로 시작하고, 캐시/연결을 정리한 후에도 Shell을 로드했다. 별도 메모리 대조 세션은 직접 연결 성공 → 같은 프록시에서 ERR_PROXY_CONNECTION_FAILED를 확인한다. 앱의 요청 허용 목록은 해제하지 않는다. 검사 후 프록시는 테스트 앱 세션에서만 복원한다. [Electron 세션 프록시 API](https://www.electronjs.org/docs/latest/api/session#sessetproxyconfig).
- 검증 방법 선택 이유: 초기 네트워크 에뮬레이션 시도에서 navigator.onLine과 대조 요청이 차단 근거가 되지 못했다. API 호출 성공만으로 통과시키지 않고 실제 연결 실패를 확인할 수 있는 프록시 조건으로 전환했다. OS 전체의 연결·방화벽·프록시 설정은 건드리지 않았다.
- 보안: 실제 CSP의 인라인 스크립트/배포 인라인 스타일 거부, CSP와 독립적인 세션 요청 차단, 알림·위치 권한 거부, 새 창·외부/파일 탐색 차단, 패키지 내 자산 경로 검사를 수행했다. 정상 화면 콘솔과 의도적 거부 시험의 진단을 분리해 기록한다. 탐색 취소는 will-frame-navigate가 먼저 처리할 수 있어 두 이벤트를 관측한다. [Electron 탐색 이벤트](https://www.electronjs.org/docs/latest/api/web-contents#event-will-frame-navigate).
- 한계: 별도 새 Windows/VM, 물리적인 네트워크 어댑터 차단, 모든 하드웨어/디스플레이/접근성 조합을 시험한 것은 아니다. PDF 자산·worker·파일 입력·학습 기능은 아직 없으며 해당 Unit에서 다시 검증한다. 서명·설치 프로그램·공개 배포는 수행하지 않는다.

### ADR-016 — 검증에서 발견한 패키징·시작·개발 서버 오류 수정

- 상태: **채택 — Unit 0.4의 환경 문제 수정**, 2026-08-31. 새로운 PDF/CBT 기능이나 권한은 추가하지 않는다.
- 기존 출력: Packager가 기존 폴더를 건너뛰고 빈 결과/성공 코드로 끝나던 동작을 확인했다. 실행 스크립트에서 먼저 출력 존재를 확인해 한국어 안내와 exit code 1로 중단하며, 반환된 패키지가 정확히 1개인지도 확인한다. 기존 결과를 자동 삭제하거나 덮어쓰지 않는다.
- 다운로드: 고정 Electron npm 패키지에 포함된 체크섬을 Packager에 전달한다. 캐시가 있을 때 체크섬을 위해 다시 네트워크에 의존하지 않으며 파일 검증은 유지한다. 캐시 없는 개발 준비의 다운로드 필요성은 그대로다.
- 필수 빌드 누락: 프로토콜 404여도 초기 탐색이 성공으로 처리되어 일반 창/exit code 0이 나왔다. main에서 dist/index.html 접근 가능 여부를 먼저 확인하도록 수정했다. 누락 시 실제 한국어 오류 대화상자와 exit code 1을 확인했다. 보안 정책을 느슨하게 하거나 오류를 숨기지 않는다.
- 개발 서버: 프로젝트 안의 테스트 프로필을 감시하다 잠긴 파일에서 EBUSY가 발생했다. 또 **/work/** 제외 규칙이 상위 work 폴더까지 일치하여 새 복사본의 index.html을 거부했다. 제외 범위를 프로젝트 내부의 .git/docs/work/.local-data/release 절대 경로에 고정하고 감시/파일 제공에서 함께 제외했다. 앱 소스는 제공하며 내부 문서·작업 자료·패키지의 HTTP 접근은 실제 403으로 거부하는지 확인했다.
- 구조: 요청 허용 판단만 electron/security.js로 추출해 직접 검사할 수 있게 했다. 실제 main에서 같은 함수를 사용하며 허용 목적지·preload API·sandbox 설정은 확대하지 않았다.
- 종료: 실제 개발 명령/패키지에서 창 표시 직후·250ms 후·1500ms 후 종료 코드 0과 포트 해제를 확인했다. 다만 패키지 250ms 종료에서 `GPU state invalid after WaitForGetOffsetInRange` 진단 2줄이 재현됐다. 보강한 검사에서 종료 전 stderr는 비어 있고 닫기 요청 후 진단이 생긴 것을 확인했다. 이후 18회 재검사가 통과해도 간헐 오류가 해결됐다고 볼 수 없다. 원인 미확정이며 그래픽 가속·sandbox·로그를 끄거나 임의 대기 시간을 넣지 않았다. 실제 Ctrl+C에서도 개발 포트가 정리됐다.
- 완료 판단: 정상 화면·보안·오프라인 검사의 성공과 종료 진단을 구분한다. 사용자 원문의 Console Error 없음 및 ROADMAP 오류 없음 기준을 낮추지 않으며 Unit 0.4/Phase 0 완료는 보류한다. PowerShell 검사 자체의 초기 ExitCode 수집 문제는 프로세스 핸들을 미리 보관해 수정했고 Windows 기본 PowerShell 5.1에서 재확인했다.
- 추가 대조: 같은 Electron 바이너리와 Shell 자산을 파일로 여는 작은 시험 창에서 요청 정책·커스텀 프로토콜 없이 39회 종료를 확인했지만 GPU 진단은 재현되지 않았다. 앱 패키지와 로딩 조건이 다르므로 특정 모듈이나 Electron/드라이버 자체를 원인으로 확정할 근거는 부족하다. 제품 코드는 이 대조를 위해 변경하지 않았다.

### ADR-017 — 명시적으로 요청된 Unit 1.1의 범위와 선행 상태

- 상태: **채택 — Unit 1.1 파일 선택 구현·기능 검사 수행**, 2026-09-01. 전체 무오류 완료 판정은 기존 종료 오류 때문에 보류.
- 근거: 사용자가 Unit 0.4 미해결 안내를 받은 뒤 Unit 1.1 진행을 명시적으로 요청했다. 파일 선택에 필요한 작업을 진행하되 Unit 0.4와 Unit 1.0을 소급 완료하거나 후속 Unit 전체의 승인으로 해석하지 않는다.
- 범위: 네이티브 파일 선택, 기본 입력 검사, 이름·크기·상태 표시, 관련 보안·원본 불변 검사. 드롭·파서·본문 표시·페이지·학습·저장은 제외한다. Unit 1.0의 유형별 전체 샘플 행렬도 만들지 않는다.
- 최소 입력 정책: 파일 크기 상한은 50 MiB(52,428,800바이트)로 임시 설정하고 같은 크기는 허용한다. 이는 성능 측정 결과나 PDF 렌더링 보장이 아니다. Unit 1.6에서 파서/렌더 성능과 함께 재검토한다.
- 완료 판단: 파일 선택 경계 36개, Electron 3경로, 실제 Windows 선택 창 검사는 통과했다. 그러나 기존 GPU 로그가 종료 검사 18회 중 1회 재현됐다. 기능 구현·검사 성공과 Unit 전체 완료를 구분하고 OPEN-09를 유지한다.
- 문서 정정: 이전 DECISIONS에서 GPU 진단과 Phase 5 저장 항목에 OPEN-07이 중복되었다. 저장 항목은 OPEN-07, GPU 진단은 OPEN-09로 분리하고 기존 GPU 참조를 정정한다.

### ADR-018 — 인자 없는 선택 API와 읽기 전용 기본 검사

- 상태: **채택 — Unit 1.1 구현·기능 검사 통과**, 2026-09-01. 당시 preload에는 selectPdfFile() 하나만 추가했고 Unit 1.2의 좁은 드롭 API는 ADR-019에서 확장했다.
- IPC: renderer에서 경로·필터·IPC 채널을 받지 않는다. main은 소유 창의 webContents, mainFrame 객체, 정확한 renderer URL과 인자 없음 조건을 검사한다. 같은 주소를 연 다른 창의 실제 요청도 거부했다. [Electron IPC 발신자 검증](https://www.electronjs.org/docs/latest/tutorial/security#17-validate-the-sender-of-all-ipc-messages).
- 선택 창: 소유 창에 연결한 비동기 showOpenDialog로 PDF 한 개만 선택하고 dontAddToRecent를 사용한다. 앱은 최근 목록·파일 경로를 따로 저장하지 않는다. Windows 자체의 대화상자 기록까지 제거하는 기능은 아니다. [Electron 파일 선택 API](https://www.electronjs.org/docs/latest/api/dialog#dialogshowopendialogwindow-options).
- 읽기: 일반 절대 Windows 경로와 .pdf 확장자를 확인한다. UNC·장치·상대 경로·대체 데이터 스트림·예약 장치 이름을 거부하며 실제 경로로 해석한 결과도 검사한다. 선택한 파일을 r 모드로 열고 같은 핸들에서 파일 여부·크기·앞 9바이트를 읽은 뒤 닫는다. 취소·중복·불신 IPC는 읽기를 시작하지 않는다.
- 서명: 첫 줄의 %PDF-1.0~1.7 또는 %PDF-2.0 뒤 CR/LF만 허용한다. 8비트 값을 보존해 검사하고 짧은 읽기를 처리한다. 앞에 다른 데이터가 붙은 비표준 파일은 수용하지 않는다. 기본 서명 통과가 구조 유효성·암호 없음·렌더링 가능을 보장하지 않는다. 파서로 손상/암호를 판정하는 일은 Unit 1.3이다.
- 결과: 이름·바이트 크기만 반환하고 원본 경로·본문·파일 핸들은 renderer에 제공하거나 이후용으로 보관하지 않는다. 파일 전체 읽기와 PDF 객체·페이지 수·documentId를 선행 구현하지 않는다. 이후 실제 렌더링 연결 시 승인된 파일의 읽기와 교체/정리 계약을 확장해야 한다.
- 상태: 선택/검사 중에는 버튼과 main 선택기를 중복 실행하지 않는다. 소유 창/프레임이 사라지거나 바뀐 뒤 도착한 선택 결과는 읽지 않는다. 성공 시 화면 메타데이터를 교체하고 취소·실패 시 이전 선택을 유지한다. 오류 코드는 한국어 상태 안내로 처리하며 개인 경로가 든 예외 메시지를 로그나 UI에 노출하지 않는다.
- UI: 파일명은 textContent로 표시하고 본문 미지원·손상/암호 미확인 상태를 명시한다. 크기는 작은 파일이 0 MiB처럼 보이지 않도록 바이트/KiB/MiB로 표시한다. 키보드 포커스와 role=status·aria-busy를 사용하며 선택은 새로고침/종료 시 초기화된다.
- 경계/한계: 현재 검사는 선택 시점의 메타데이터다. 파일 감시·강한 변경 잠금은 없다. 매핑 드라이브나 클라우드 자리표시자의 실제 저장 매체 판별까지 구현하지 않았으며 로컬 디스크 시험만 수행했다. 파일 경로 허용 목록 검사만으로 모든 네트워크 저장소 접근을 차단했다고 주장하지 않는다.
- 검증: 실제 파일의 해시·수정 시각, 잘못된 서명·고비트 서명·빈 파일·크기 경계·핸들 정리·실패 재시도·다른 창 발신자를 확인했다. 패키지에서는 생성한 시험 파일의 읽기 권한만 일시 거부하고 정확히 복원해 실제 접근 거부 안내와 복원 후 동일 해시를 확인했다. 개인 파일 권한은 변경하지 않았다.
- 도구 구분: Electron 3경로 검사는 native dialog 결과를 제어하지만 IPC·파일 읽기·UI는 실제로 실행한다. test:native는 별도로 실제 Windows 대화상자의 선택·취소를 확인한다. UI 자동화 패턴이 없는 기본 컨트롤은 해당 앱 소유 대화상자 안에서 확인한 핸들만 사용한다. 테스트의 디버그 연결·권한 fixture·UI 제어는 제품 패키지에 포함하지 않는다.

### ADR-019 — 실제 File 기반 드롭과 파일 선택 검사 경로 공유

- 상태: **채택 — Unit 1.2 구현·기능 검사 통과**, 2026-09-01. 전체 무오류 완료 판정은 OPEN-09 때문에 보류.
- 범위: Windows 탐색기의 로컬 PDF 한 파일 드롭, 드롭 상태 표시와 한국어 결과 안내만 추가한다. 다중 파일 일괄 처리·폴더 탐색·URL 다운로드·PDF 파싱/렌더링·저장은 구현하지 않는다.
- 경로 경계: 폐기된 File.path에 의존하지 않고 sandbox preload의 Electron `webUtils.getPathForFile(file)`을 사용한다. renderer는 실제 File 객체 배열만 전달하고 preload가 얻은 경로는 고정 IPC로 즉시 main에 보내며 renderer에 반환하지 않는다. 메모리에서 생성해 디스크 경로가 없는 File은 빈 경로로 거절한다. [Electron webUtils](https://www.electronjs.org/docs/latest/api/web-utils).
- IPC: main은 선택과 별도의 고정 채널에서도 소유 webContents·mainFrame 객체·정확한 URL·인자 개수와 배열/문자열을 검사한다. raw ipcRenderer·범용 경로 입력·파일 읽기 API는 노출하지 않는다. 다른 창/프레임, 잘못된 인자와 늦게 완료된 요청은 결과를 적용하지 않는다.
- 동일 검사: 한 파일의 드롭 경로는 Unit 1.1의 `inspectPdfFile`에 연결한다. 일반 로컬 경로·확장자·실제 경로·파일 여부·50 MiB·첫 줄 서명·읽기 전용 핸들·변경 감지를 그대로 적용하고 이름/크기만 반환한다. 폴더는 같은 검사에서 NOT_A_FILE로 거절한다.
- 거절 정책: renderer는 파일이 없는 URL 드롭과 빈 전송, 다중 드롭을 읽기 전에 거절한다. main도 빈 배열·다중 경로·빈 경로를 별도로 거절한다. 실패·취소는 직전 성공 정보를 유지하며 개인 경로나 예외 메시지를 표시하지 않는다.
- 순서: 파일 선택과 드롭은 main의 같은 실행 잠금과 UI의 같은 진행 상태를 공유한다. 선택 창이 늦게 끝나거나 드롭 검사가 겹쳐 이전 요청이 최신 화면을 덮지 않는다.
- UI/접근성: 문서 작업 공간에 드롭 안내와 시각적 drag-over 상태를 추가한다. 상태는 role=status 문구로도 전달하고 기존 PDF 선택 버튼을 키보드 대안으로 유지한다. 브라우저 기본 드롭 탐색은 막지만 앱의 기존 탐색/새 창 제한을 완화하지 않는다.
- 검증: 경계 검사 43개와 Electron 개발·빌드·패키지 3경로에서 실제 디스크 파일 drag event, 다중 파일·폴더·URL·빈 경로·빈 전송, 원본 해시·이전 선택 유지·발신자·입력 경쟁을 확인했다. 실제 Windows 선택 창 회귀도 통과했다. GUI 검사는 사용자 Windows 실행 환경에서 수행했으며 제품의 GPU·sandbox·네트워크 설정은 변경하지 않았다.
- 제한: Windows 탐색기 기반 로컬 파일만 검증했다. 브라우저/메일의 가상 항목, shell namespace, 클라우드 자리표시자·매핑 드라이브의 실제 저장 매체 판별은 보장하지 않는다. 파일 감시·PDF 구조 판정·본문 표시와 열린 문서 핸들 수명은 후속 Unit 범위다.

## 6. 확인한 자료와 해석의 한계

기술 근거 링크는 각 주장 가까이에 기재했다. PDF.js 공식 API·소스·예제와 Electron 공식 문서를 확인했으며, Unit 0.2에서 Node.js LTS·Vite 요구사항과 실제 npm 패키지의 engines/exports를 다시 확인했다.

위 자료는 사용할 API와 프로세스 경계를 뒷받침한다. **규칙 기반 CBT 인식률, 우리 마스크의 안전성, 특정 PDF 호환성, 성능은 이 프로젝트에서 아직 시험하지 않았다.** 이 문서의 인식 방법·MVP 제한·실패 정책은 공식 라이브러리가 보장한 기능이 아니라 프로젝트 설계 제안이다.
